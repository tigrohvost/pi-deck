# Ускорение агента, инференса и интерфейса — октябрь 2026

Дата: 2026-10-07. Устройство: Samsung SM-S918B, Android 16, Snapdragon 8 Gen 2,
12 GB RAM. Замеры выполнены стендом [`tools/adb_runtime_experiments.py`](../tools/adb_runtime_experiments.py):
стоковый `llama-server` b10092 из `app/src/main/jniLibs` запускается под UID
shell в `/data/local/tmp/pideck-opt` с теми же аргументами, что строит
`ModelSpec`, поэтому установленное приложение в замерах не участвует.
Модель для стоковых опытов — LFM2.5 2.6B QAD Q4_0 (SHA-256
`a247afd6…8d40b03`, сверена на телефоне). Телефон во время опытов использовался
и был тёплым (40–45 °C перед прогонами), поэтому все сравнения парные, а
порядок вариантов чередуется. Сырые отчёты лежат в `benchmarks/out/opt-*`.

## Агентный цикл

**Продление AUTONOMOUS.** Мост сравнивал `autonomousUntilMs` при каждом
`bridge-start`, а окно живёт не дольше 30 минут, поэтому продление разрешения
перезапускало Pi: холодный старт Node и полный prefill истории. Pi это поле не
читает, его проверяет только сам мост при `PROMPT`. Теперь `bridge-start` с
тем же контрактом и новым окном вызывает аутентифицированный `POST /v1/grant`
работающего моста и обновляет метаданные; при отказе остаётся прежний точный
перезапуск. Профиль по-прежнему меняется только перезапуском.

**Стабильная схема инструментов.** Раньше узкая первая задача сессии (погода,
навигация, ограниченный ремонт) давала узкую схему, а следующая обычная задача
дописывала инструменты. Схема входит в системный блок, поэтому кэш отключался
и вся история заново проходила prefill. Теперь базовый набор профиля
выставляется на `session_start`; сужение под задачу, как и раньше, обеспечивает
проверка `tool_call` и заметка `PI//DECK TASK TOOLS`. Цена — 300–900 токенов
для узкой первой задачи, которые к тому же переиспользуются между сессиями.

**Префикс между сессиями.** b10092 сохраняет чекпоинты рекуррентного состояния
во время prefill и восстанавливает подходящий, если новый запрос расходится с
содержимым слота. `pideck-local-cache.ts` разрешает `cache_prompt` первому
запросу новой сессии, только если системное сообщение и контракт запроса
побайтно совпадают с предыдущим запросом; включается переменной
`PIDECK_CROSS_SESSION_PREFIX`, которую мост выставляет для пары `stock`/`b10092`.

| Запрос, контекст 1433–1439 токенов | `cache_n` | `prompt_n` | Prefill |
|---|---:|---:|---:|
| Новая сессия, повторное использование | 917 | 522 | 6,75 с / 8,92 с |
| Тот же запрос без кэша | 0 | 1439 | 18,52 с / 20,85 с |
| После запроса с другим системным промптом | 923 | 508 | 8,90 с / 7,35 с |

Два прогона: ускорение 2,74× и 2,34×. Рассуждение, текст и вызов инструмента
(имя и аргументы) совпали побайтно с полным prefill. Восстанавливается 917 из
≈ 1415 токенов префикса, потому что первый чекпоинт ставится за
`n_ubatch + 4` токенов до конца первого запроса, а чекпоинт на границе
сообщения пользователя вытесняется правилом `checkpoint_min_step`. Закрепить
чекпоинт ровно на границе префикса можно отдельным патчем сервера — это
следующий шаг. После запроса с другим системным промптом (Chat, сжатие)
состояние агента возвращается из RAM-кэша промптов.
[Отчёт](../benchmarks/out/opt-prefix-reuse-lfm-qad-sm-s918b-2026-10-07.json).

**Снимок префикса на диск.** Старый опыт в [performance.md](performance.md#why-a-disk-slot-cache-is-not-enabled)
восстанавливал слот и отправлял *тот же* промпт: сервер обязан пересчитать хотя
бы последний токен, а рекуррентное состояние откатить нельзя, поэтому был
`cache_n=0`. Если же слот содержит ровно системный префикс (текст до маркера
хода пользователя из `/apply-template`), следующий запрос его строго
продолжает и отката не требуется. Опыт `slot-snapshot`, LFM2.5 QAD:

| Шаг | Результат |
|---|---|
| Префикс | 1414 токенов, 18,3 с, снимок 22,5 МБ, сохранение 9 мс |
| Новый процесс сервера, восстановление | 31 мс, `n_restored` 1414 |
| Первый запрос | `cache_n` 1414, `prompt_n` 25, prefill 0,49 с, всего 4,3 с |
| Тот же запрос в холодном сервере | `prompt_n` 1439, prefill 21,1 с, всего 25,1 с |

Ответ совпал. Теперь приложение запускает стоковый сервер с
`--slot-save-path` в кэше (хранятся четыре последних снимка), а
`pideck-local-cache.ts` на первом запросе сессии или процесса Pi
восстанавливает снимок по ключу из SHA-256 модели, контракта запроса и
системного сообщения. Если снимка нет, префикс вычисляется один раз и
сохраняется — это та же работа, которую иначе сделал бы сам запрос. Если
снимка нет, но in-memory чекпоинт уже покрывает часть префикса, префикс заново
не считается. Запросы идут только на loopback-сервер приложения с его ключом;
любая ошибка возвращает прежнее поведение.
[Отчёт](../benchmarks/out/opt-slot-snapshot-lfm-qad-sm-s918b-2026-10-07.json).

**Сжатие контекста.** `pideck-context-guard.ts` заменял старые копии
одинаковых результатов `read` маркерами при любой экономии от 4 КБ, что
отключало кэш и вызывало полный prefill ради ~1 тыс. токенов. Теперь замена
выполняется только при заполнении окна от 70% (по `getContextUsage()` Pi или по
оценке размера сообщений); без известного окна поведение прежнее.

**Холодный старт.** При включённом автозапуске, подтверждённой ранее связи,
актуальном runtime и точно остановленном ядре загрузка модели начинается сразу,
а не после проверки Termux. Связь всё равно проверяют `server-adopt` и запуск
моста. Проверка runtime больше не запускает Node ради `pi --version`: версия
читается из `package.json` пакета, на который указывает ссылка, с откатом на
прежний способ. Запуск моста параллельно с загрузкой модели не делался: по
прежним замерам он занимает 0,5–1,0 с и потребовал бы постоянного ключа API.

**Промпт.** Базовый промпт, `MOBILE_AGENT_GUIDANCE` и `AGENTS.default.md`
повторяли идентичность, язык, правила путей и отчёта. Каждое правило теперь
сказано один раз; подсказки для `web_research`, `weather` и
`pideck_replace_lines` перенесены в описания этих инструментов и попадают в
промпт только вместе с ними. Неизменённый пользователем `AGENTS.md` v2
обновляется до v3 по SHA-256; изменённый не трогается. Контракт runtime
поднят до 58.

## Инференс

**`--no-mmap` для перепаковываемых моделей.** b10092 на ARM с i8mm/dotprod
перепаковывает Q4_0, Q4_K, Q5_K и Q6_K в анонимную память, а страницы файла
остаются отображёнными. LFM2.5 QAD, контекст 10240, два раунда:

| Вариант | RSS | RssAnon | RssFile | Prefill, ток/с | Декодирование, ток/с |
|---|---:|---:|---:|---:|---:|
| mmap | 3,40 ГБ | 1,85 ГБ | 1,55 ГБ | 83,6 / 78,4 | 16,6 / 16,3 |
| `--no-mmap` | 2,07 ГБ | 2,06 ГБ | 0,01 ГБ | 80,0 / 67,8 | 16,6 / 16,4 |

Минус 1,33 ГБ (−39%) без потери скорости декодирования. Второй prefill
`--no-mmap` шёл последним, на самом тёплом телефоне; механизма замедления
вычислений у этого флага нет. Флаг добавлен всем стоковым Q4_0/Q4_K_M;
Bonsai Q1_0 не перепаковывается и оставлен с mmap. Измеренные пики памяти в
каталоге сняты с mmap и для проверки памяти остаются консервативными.
[Отчёт](../benchmarks/out/opt-memory-mmap-lfm-qad-sm-s918b-2026-10-07.json).

**RAM-кэш промптов.** По умолчанию b10092 разрешает до 8192 МиБ сохранённых
состояний слота. На телефоне с 12 ГБ это путь к давлению на память, поэтому
стоковым моделям задан `--cache-ram 512`. Bonsai 2 поднят с 256 до 512 МиБ:
его состояние занимает около 450 МиБ и раньше не помещалось никогда.

**Пул prefill.** Три чередующиеся пары, промпт 3477 токенов:

| Пул | Prefill, ток/с | Температура после | Запас частоты после |
|---|---:|---:|---:|
| 8 потоков, CPU 0–7 | 78,5 / 77,3 / 81,1 (79,0) | 83,1 °C | 0,70 |
| 5 потоков, CPU 3–7 | 76,0 / 76,8 / 74,7 (75,8) | 78,9 °C | 0,75 |

Пять больших ядер греют меньше, но медленнее на 4%; выигрыша в скорости от
меньшего нагрева в этих прогонах не видно. Рабочий профиль не изменён.
[Отчёт](../benchmarks/out/opt-batch-threads-lfm-qad-sm-s918b-2026-10-07.json).

**KV-кэш q8_0.** Две чередующиеся пары поверх аргументов каталога (уже с
`--no-mmap`), промпт 3477 токенов:

| KV | RSS | Prefill, ток/с | Декодирование, ток/с |
|---|---:|---:|---:|
| f16 | 2,075 ГБ | 73,7 / 78,6 | 14,7 / 15,4 |
| q8_0 | 1,999 ГБ | 38,6 / 40,7 | 12,0 / 13,2 |

У LFM2.5 кэш внимания есть лишь у части слоёв, поэтому экономия всего 76 МБ, а
квантованный KV на CPU вдвое замедляет prefill. Не внедрено.
[Отчёт](../benchmarks/out/opt-kv-quant-lfm-qad-sm-s918b-2026-10-07.json).

**Prism для Bonsai 2.** Скрипт `tools/build_prism_android.sh` теперь накладывает
закреплённый набор патчей `pideck-prism1` из `third_party/prism/patches`
(SHA-256 проверяется скриптом и задачей `verifyNativeRuntime`): повторная
попытка строгой привязки потока при `EINVAL` и разбор блока PTQ1_0 один раз для
двух токенов промпта через NEON SDOT. Сравнение ABBA тем же GGUF (SHA-256
`53107f53…fe33ee3`), промпт 170 токенов, CPU, аргументы каталога:

| Сборка | Prefill, ток/с | Привязка потоков |
|---|---:|---|
| prism-842b188 (было) | 0,851 / 0,817 | два потока не закреплены (`EINVAL`) в обоих прогонах |
| prism-842b188 + pideck-prism1 | 1,342 / 1,630 | закреплены, при первом старте после 2 повторов |

Среднее ускорение prefill ×1,78, ответ совпал побайтно. В эту цифру входят и
ядро (в исследовании ×1,46–1,52 при уже правильной привязке), и исправление
привязки. Скорость декодирования здесь не оценивалась: ответ из двух токенов
слишком короткий; ядро меняет только путь с двумя токенами, одиночный токен
идёт прежним кодом. Новый ELF (SHA-256 `402f8118…a17b75`) закреплён в
`native-runtime.json` и `compatibility.json`.
[Отчёт](../benchmarks/out/opt-prism-kernel-bonsai2-sm-s918b-2026-10-07.json).

## Интерфейс

- Транскрипт хранится в отдельном файле `transcript-v1.json` и пишется не чаще
  раза в 750 мс в фоновом потоке. Курсор моста, который обновляется на каждом
  событии, вынесен в отдельный маленький файл настроек. Старый транскрипт
  переносится один раз.
- Пульсации на время хода затухают через несколько циклов вместо бесконечной
  анимации. Сетка фона кэшируется в аппаратном слое, развёртка рисуется одним
  прямоугольником с `BitmapShader` вместо ~770 линий на кадр. На время
  инференса окно просит 60 Гц.
- `refreshUi` не опрашивает DownloadManager, когда приватная копия модели уже
  установлена. Чистка журнала операций больше не разбирает все записи при
  каждом результате и работает с гистерезисом 100 → 80. Две записи с `fsync`
  при отправке оставлены намеренно: запись операции должна быть надёжной до
  отправки.
- Прогресс: строки `prompt processing … progress …` и `n_decoded …` из
  собственного лога сервера показывают «Читаю промпт 64% · 94 ток/с · ~6 с» и
  «Думаю · 120 ток.». Метка загрузки сообщает время прошлой загрузки модели.
  Этап хода хранится в одном поле `TurnPhase`, и обновление состояния больше не
  стирает текущий инструмент.
- «Стоп» закреплён над полем ввода; пустая кнопка отправки во время работы
  становится «■». Останавливаются ход агента, сжатие (мост завершает процесс Pi,
  история не меняется) и загрузка модели. Запрос из очереди можно вернуть в
  поле ввода.
- Ответы рендерятся как Markdown: блоки кода с прокруткой и кнопкой
  «Копировать», заголовки, списки, жирный текст и inline-код. Долгое нажатие
  выделяет часть текста. «Отправить» под ответом переименовано в «Поделиться»;
  у своего сообщения есть меню «Изменить и отправить / Повторить /
  Копировать», после ошибки хода — «Повторить запрос».
- Новый вывод не тянет ленту вниз, если пользователь читает выше: появляется
  «↓ Новое».
- Служебные строки запуска показываются в одной строке состояния и не
  занимают лимит транскрипта. Строки инструментов раскрываются нажатием,
  контраст статуса поднят.
- Сессии: при возобновлении показываются последние сообщения, сессию можно
  переименовать (локально) и убрать в архив. «Назад» с экранов Ядро и Сессии
  возвращает к разговору.
- Около 170 строк интерфейса, уведомлений и ошибок получили английский
  вариант. Цели касания — не меньше 48 dp; вкладки и фаза хода доступны
  TalkBack.
- Из `MainActivity` вынесены хранение транскрипта, построение экрана «Сессии»
  (`SessionsScreen`), разбор прогресса (`ServerProgress`), Markdown и модель
  этапа хода (`TurnPhase`); все они покрыты JVM-тестами.

## Проверка на телефоне

Release-сборка, подписанная локальным ключом устройства, установлена поверх
рабочего приложения (`adb install -r`, данные сохранены). Приложение само
обновило Termux-runtime до контракта 58, автозапуском загрузило выбранную
Qwen3.8 4B Distill и ответило на запрос агента; транскрипт перенёсся из старых
настроек. Instrumentation-тесты раскладки, сохранения промпта и операций прошли
на SM-S918B, включая новый тест блоков кода и целей касания 48 dp.

Проверка выявила ошибку, внесённую ранним стартом модели: мост в Termux,
переживший переустановку приложения, переиспользовался, а его Pi держал старый
ключ API сервера, и ход завершался `401`. Теперь мост запоминает SHA-256 ключа
сервера и перезапускается при его смене; после исправления ход прошёл.

На той же сессии (3,95 тыс. токенов контекста) первый ход после перезапуска
сервера и Pi без снимка префикса занял около 3 минут, а со снимком — около
50 секунд. Это грубый замер по опросу интерфейса и один прогон; точные числа
механизма — в опыте `slot-snapshot` выше.

```sh

  --model-path /data/local/tmp/pideck-opt/LFM2.5-2.6B-QAD-Q4_0.gguf \
  --output benchmarks/out/opt-prefix-reuse.json --max-celsius 52 --max-tokens 64
python3 tools/adb_runtime_experiments.py memory --repeats 2 --max-celsius 50 \
  --model-path /data/local/tmp/pideck-opt/LFM2.5-2.6B-QAD-Q4_0.gguf \
  --output benchmarks/out/opt-memory.json
python3 tools/adb_runtime_experiments.py batch-threads --repeats 3 --max-celsius 46 \
  --model-path /data/local/tmp/pideck-opt/LFM2.5-2.6B-QAD-Q4_0.gguf \
  --output benchmarks/out/opt-batch-threads.json
python3 tools/adb_runtime_experiments.py slot-snapshot --max-celsius 50 --max-tokens 64 \
  --model-path /data/local/tmp/pideck-opt/LFM2.5-2.6B-QAD-Q4_0.gguf \
  --output benchmarks/out/opt-slot-snapshot.json
python3 tools/adb_runtime_experiments.py prism-kernel --model-id bonsai2-27b \
  --model-path /data/local/tmp/bonsai2.gguf --filler 6 --max-tokens 12 \
  --baseline-binary old/libpideck_prism_server.so \
  --candidate-binary app/src/main/jniLibs/arm64-v8a/libpideck_prism_server.so \
  --output benchmarks/out/opt-prism-kernel.json
```
