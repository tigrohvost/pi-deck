# Ускорение Bonsai 2 27B на SM-S918B

Дата исследования: 2026-09-24. Проверены исходники, машинный код установленной
сборки, локальный GGUF и документация Prism. После подключения телефона
выполнены CPU-бенчмарки и профилирование на SM-S918B / Android 16.
Числа, команды, SHA сборок, память, частоты и маски потоков сохранены в
[отчёте замеров](../benchmarks/out/bonsai2-ptq1-cpu-sm-s918b-2026-09-24.json).

Практический результат: повторная привязка потоков устраняет часть сбоев
старта, но пока недостаточна для переноса в приложение как готовое решение.
В отдельном тестовом APK обнаружены изменения фактических масок уже во
время работы, в том числе без предупреждений affinity (см. продолжение ниже).
У исправно распределённых потоков измерено примерно 0,77–0,98 ток/с decode
на пяти ядрах и 1,18–1,19 ток/с prefill на восьми. Уменьшение microbatch и PR #249
заметного преимущества не показали. Mmap следует сохранить.

Продолжение исследования: проверены CPU-ядра и Vulkan на том же телефоне.
Новый PTQ-шейдер PR #252 поднял короткий GPU decode с 0,245 до 0,576 ток/с
в паре запусков, но превосходства над рабочим CPU пока нет. Стандартный
PQ2 ARM-путь оказался медленным; ручной PQ2 NEON быстрее PTQ примерно
в 1,4 раза в микробенчмарке. В полном тесте PQ2 ускорил короткий prefill,
но ухудшил decode при нагреве и повторном чтении весов с накопителя;
детали и ограничения приведены ниже.
[Данные продолжения](../benchmarks/out/bonsai2-next-hypotheses-sm-s918b-2026-09-24.json).

## Модель и первоначальный запуск

Модель: `Ternary-Bonsai-2-27B-PTQ1_0.gguf`, 5 946 648 928 байт,
SHA-256 `53107f530aa52eb00912263ab1ee29bd199261c87cd7b4ad4ca1318c1fe33ee3`.
Движок: Prism `842b1880415d6f508f03b789e5ce70194def7bfd`, Android arm64,
`-O3`, `armv8.2-a+dotprod+fp16`, CPU. Vulkan/OpenCL отключены при сборке.

| Проверка | Результат | Ограничение |
|---|---:|---|
| Отдельный сервер через ADB, загрузка | около 125 с | Первый запуск во время настройки |
| Тот же сервер, обработка 23 токенов промпта | 141,79 с; 0,162 ток/с | Один образец, без контроля температуры и давления на память |
| Тот же сервер, ответ `BONSAI_OK` | 6 токенов; 0,385 ток/с по server timings | Слишком короткий ответ для устойчивой оценки |
| Установленный release APK, Chat | `BONSAI_OK`; UI показал 1,0 ток/с | 6 токенов, иной путь запуска и иной промпт |

Разница между последними двумя строками не доказывает эффект отдельной
оптимизации. Нужен одинаковый запрос, состояние кэша и тепловой режим.
Подробности установки сохранены в [model-admission.md](model-admission.md#bonsai-2-27b-bonsai2-27b).
Локальные свидетельства: `build/device-bonsai/preflight-response.json` и
`build/device-bonsai/bonsai2-running.png`.

## Сравнительные CPU-замеры

Использован `llama-bench` из той же версии Prism, отдельный процесс ADB
с UID shell. Нативный сервер приложения остановлен. Это синтетическая
обработка короткого контекста, а не измерение TTFT в приложении с контекстом
4096. Установленный APK и его runtime во время экспериментов не менялись.

Перед каждым запуском проверялось восстановление лимита частоты большого
ядра до 98% номинала и температура вычислительных датчиков не выше 47 °C.
В длинных запусках телефон снова снижал лимит с 3,36 до 1,59–2,23 ГГц.
Это лимит `scaling_max_freq`, а не непрерывное измерение фактической частоты.
Охлаждение до порога не гарантирует одинакового прогрева корпуса.

Первые диагностические запуски читали модель из `/sdcard/Download`, затем
использовалась отдельная копия в `/data/local/tmp` с проверенной SHA-256.
Основные параметры: CPU, `-b 256`, `-ub 128`, стандартный warmup, mmap/auto,
один измеряемый образец, кроме явно указанных вариантов и повторов.
Кэш файлов не сбрасывался: различия
видны по `read_bytes` и major faults. Пользователь подтвердил, что оставит
телефон в покое; последующие повторы выполнялись после этого подтверждения.

Во время серии decode экранное приложение не фиксировалось. Перед серией
prefill PI DECK был на переднем плане и создавал нагрузку интерфейса при
остановленном модельном сервере; для всех трёх prefill-вариантов его
свернули на главный экран. Показатели двух серий поэтому не следует
использовать для прямого сравнения стоимости одного входного и выходного
токена в приложении.

| Генерация 64 токенов, общая маска CPU 3–7 | Токенов/с |
|---|---:|
| 3 потока | 0,676 |
| 4 потока | 0,818 |
| 5 потоков, первый запуск | 0,893 |

Эти одиночные результаты не дают точного коэффициента ускорения.
Каждый запуск включает собственную загрузку и прогрев; на скорость также
влияют остаточное тепло и вытеснение страниц модели.

### Привязка и размещение потоков — подтверждённая причина провалов

В двух диагностических запусках с пятью строго закреплёнными потоками
Android-вызов `sched_setaffinity` вернул `EINVAL`. В одном из них поток, которому
предназначалось CPU 6, сохранил маску 0–7 и большую часть профилируемого
фрагмента делил CPU 7 с главным потоком. По `/proc` остальные потоки были
закреплены корректно. Ухода этого потока на малые ядра профиль не показал.

В десятисекундном фрагменте более 90% выборок пользовательского CPU-времени
пришлись на ожидание в барьерах: адреса внутри `ggml_graph_compute_thread`
и `ggml_compute_forward_mul_mat` разрешаются в инлайн-код
`ggml_thread_cpu_relax` / `ggml_barrier`. Это доля выборок данного фрагмента,
а не доля полного времени запроса.

При `--cpu-strict 0 -C f8` каждый поток получил общую маску быстрых CPU 3–7;
ошибки affinity в этих проверках отсутствовали. В отдельном пятисекундном
профиле 89,38% выборок уже приходятся на `ggml_vec_dot_ptq1_0_q8_0`.
Профилирование: `simpleperf`, `cpu-clock:u`, 99 Гц, потерянных выборок нет.

Скорость плохого строго закреплённого случая — 0,320 ток/с, следующего
запуска с общей маской — 0,893 ток/с. Но первый процесс прочитал с накопителя
16,49 GB, второй — 1,09 GB. Поэтому приписывать всю разницу одной настройке
affinity нельзя. Ошибка зафиксирована в бенчмарке под UID shell.

Повтор с общей маской обнаружил другую проблему: без ошибок affinity два
рабочих потока делили CPU 7, и снова почти все выборки приходились на барьеры.
Из 1983 выборок только 40 (2,02%) попали в PTQ dot product. Затем в этом же
процессе через `taskset` каждому потоку назначили отдельный CPU 3–7. Все
пять назначений прошли успешно; следующий профиль показал 2332 из 2476
выборок (94,18%) в PTQ dot product и правильное распределение по ядрам.
Таким образом, одна общая маска не обеспечивает устойчивого результата.
Агрегированная скорость этого запуска исключена из сравнения: настройки
изменены посреди измерения.

Подготовлен [экспериментальный патч повторной привязки](../benchmarks/out/bonsai2-affinity-retry-2026-09-24.patch):
при Android `EINVAL` повторить запрос до 20 раз с паузой 10 мс, затем
сохранить обычную диагностику ошибки. Он применяется только при создании
или активации пула, не меняет математику модели и не включён в APK.
Проверять надо не только отсутствие предупреждения, но и фактические
маски каждого потока.

В первом полном запуске с этим патчем отказ был устранён после двух
повторов (около 20 мс), и `/proc` подтвердил пять отдельных CPU. Результат
генерации 64 токенов — 0,896 ток/с. Сам патч устраняет наблюдавшийся сбой
старта; большой коэффициент ускорения относительно уже корректно
распределённых потоков из этого результата не следует.

Повторный запуск без PR #249 дал **0,973 и 0,766 ток/с** в двух
последовательных образцах. Между ними телефон не охлаждался; к концу
лимит большого ядра снизился до 1,59 ГГц. Дополнительное чтение с накопителя
за весь процесс — всего 9,8 MB. Перед измерениями удалось восстановить
affinity одной повторной попыткой. В трёх независимых стартах серии decode
на обеих сборках
с патчем понадобились соответственно 2, 2 и 1 повтор; все завершились
корректным распределением пяти потоков. Это короткая проверка, а не
гарантия при любом тепловом режиме или CPU-set приложения.

### Отказ от mmap ухудшил работу памяти

Эксперимент `-lm none` остановлен: примерно через 41 с у процесса было
3 058 868 KiB swap (около 2,92 GiB), а системный `memory PSI full avg10`
достиг 13,86%. Завершённого измерения токенов/с нет. Для этой конфигурации
рекомендуется сохранить mmap. Лимит `mlock` shell-процесса — 64 MiB,
чего недостаточно для закрепления почти 6 GB весов в RAM.

### Обработка промпта и microbatch

Отдельная серия: 64 входных токена, `-b 256`, одинаковая сборка с повторной
affinity, стандартный warmup, затем один измеряемый prefill. Перед каждым
вариантом восстановлены частота и температура по описанному выше порогу.
PI DECK свёрнут на главный экран во всех случаях этой серии.

| Потоки / CPU | `-ub` | Prefill, ток/с |
|---|---:|---:|
| 5 / 3–7 | 128 | 1,060 |
| 8 / 0–7 | 128 | 1,178 |
| 8 / 0–7 | 32 | 1,189 |

Здесь `-ub 128` позволяет обработать все 64 токена одним microbatch;
`-ub 32` разбивает их на два. Это проверка короткого промпта. Для длинной
истории и контекста 4096 нужны замеры в приложении.

Восемь потоков дали на 11,2% больше пяти в этой паре запусков; повторов
для точной оценки величины выигрыша нет. Изменение microbatch на восьми
потоках дало всего 0,93%, что не доказывает улучшения. Разумно сохранить
текущие восемь потоков batch и `-ub 128`, отдельно проверив более длинные
запросы. Во всех трёх случаях swap процесса оставался нулевым по снимкам.
В последнем запуске снова сработали две повторные попытки affinity.
Всего шесть запусков экспериментальных сборок завершились с правильными
масками потоков; в четырёх потребовались повторы, в двух привязка прошла сразу.

## Продолжение: CPU-ядра и Vulkan

### CPU: сравнение одинаковых троичных весов

[Исходник пробы](../benchmarks/out/bonsai2-quant-kernel-probe-2026-09-24.cpp)
использует статические CPU-библиотеки установленного Prism. Синтетические
веса точно представимы в PTQ1 и PQ2, имеют значения `-scale, 0, +scale`,
разные степени двойки в качестве масштабов и полностью нулевую первую
строку. Для 33 строк каждой формы проверены точное восстановление весов
и dot product относительно суммы в float64 после деквантования активаций.
Максимальная ошибка, нормированная на сумму абсолютных произведений,
в последней пробе шести алгоритмов — `2,25e-8`, порог `3e-6`.
Это шесть **алгоритмов**, выполняемых последовательно на одном CPU 3.

Проверены ширины 5120, 6144, 17408 и 256/8192 строки матрицы. Для каждого
алгоритма — три образца не короче 300 мс, порядок меняется между образцами.
Веса занимали от 0,27 до 36,1 MiB на формат. Это не 6–7 GB всей модели,
не многопоточная нагрузка и не сравнение качества ответов. До/после серий
сохранены температуры; частоты не фиксировались.

| Алгоритм, ширина 5120, 8192 строки | Медиана, нс на вес | Скорость относительно PTQ |
|---|---:|---:|
| Исходный PTQ1 × Q8_0 | 0,1325 | 1,00× |
| Стандартный PQ2 × Q8_K | 0,5624 | 0,24× |
| Существующий ручной PQ2 × Q8_0 NEON | 0,0942 | 1,41× |
| PTQ1 с одним NEON-накопителем | 0,1420 | 0,93× |
| PTQ1 с двумя NEON-накопителями | 0,1359 | 0,98× |
| PTQ1 с четырьмя NEON-накопителями | 0,1445 | 0,92× |

Во всех шести формах первой серии ручной PQ2 дал 1,39–1,41× скорости PTQ;
стандартный PQ2 был примерно в 4,2–4,3 раза медленнее. Простая замена GGUF
на официальный PQ2 при текущем ARM dispatch поэтому не обоснована.
Для варианта с Q8_0 выполнена проверка полной модели ниже: PQ2 увеличил
веса примерно на 1,26 GB и не дал выигрыша генерации в этой конфигурации.

Экспериментальные PTQ-функции сохраняют исходную распаковку и заменяют
скалярные редукции на NEON-накопители. Выигрыша не обнаружено, в движок
они не включены. Первая версия пробы по ошибке использовала программную
конверсию FP16 и была медленнее на 37%; этот результат исключён. Исправленная
версия использует тот же `GGML_CPU_FP16_TO_FP32`, что и baseline; машинный
код содержит аппаратный `fcvt`. Все строки таблицы относятся к исправленному
варианту.

Попытка закрепить одиночную пробу на CPU 7 не прошла даже за 20 вызовов
с паузами 10 мс; измерений для этого ядра нет. CPU 3 успешно назначался
с первой попытки. Это дополнительное ограничение предыдущего affinity-патча:
его успех в шести стартах thread pool не гарантирует доступность CPU
в любом состоянии Android. Проверка фактических масок остаётся обязательной.

### Локальная перепаковка полной модели в PQ2

Из исходного PTQ1 создан отдельный исследовательский GGUF размером
**7 206 168 928 байт** (+1 259 520 000 байт), SHA-256
`3907dc1658db1f78a9826bf8d5bcb8dc65db0d466388937af57f2294fae62ec1`.
Это локальная перепаковка исходных весов, а не скачанный официальный PQ2.
[Исходник конвертера](../benchmarks/out/bonsai2-pq2-repack-2026-09-24.cpp).

Конвертер меняет base-3 на двухбитную упаковку и копирует FP16-масштабы.
Обратное отображение проверено для всех **26 869 760 000** троичных весов
402 тензоров. Ещё 449 тензоров F32/BF16 сравнены побайтно с оригиналом.
В заголовке изменены только `general.file_type` (143 → 141), типы PTQ-тензоров
(143 → 142) и смещения. Размерности, tokenizer, chat template, Hadamard
и остальные метаданные сохранены. Перед запуском SHA проверена и на телефоне.

[Экспериментальный ARM-патч](../benchmarks/out/bonsai2-pq2-arm-q8-2026-09-24.patch)
выбирает существующий `PQ2_0 × Q8_0` при `__ARM_NEON`; на остальных
архитектурах оставляет прежний выбор. Сборка также содержит предыдущую
повторную affinity. Эта пара модели и движка предназначена для замеров;
установленное приложение пока использует исходный PTQ1 и прежний runtime.

На одной и той же сборке выполнен последовательный A/B-тест: сначала PQ2,
затем PTQ1; четыре строго закреплённых CPU 3–6, `-dev none`,
`-ngl 0 -nopo 1 -nkvo 1`, `-b 256 -ub 4`, промпт 16, генерация 32,
один образец после warmup. Перед обоими стартами максимумы CPU 3–6 были
2,8032 ГГц, CPU 7 — 3,36 ГГц, самый горячий вычислительный датчик — 46,9 °C.
Маски проверены через `/proc`; ошибки привязки устранены повторными попытками.

| Полная модель, четыре CPU | Prefill 16, ток/с | Decode 32, ток/с | Чтение с накопителя за процесс |
|---|---:|---:|---:|
| PQ2 + ARM Q8_0 | 1,206 | 0,462 | 15,10 GB |
| PTQ1, контроль той же сборкой | 0,959 | 0,696 | 5,98 GB |

В этой паре PQ2 улучшил prefill на 25,8%, но снизил decode на 33,6%.
Оценка по одному запуску не устанавливает устойчивый процент. PQ2 после
загрузки неоднократно перечитывал веса; RSS менялся примерно от 5,83 до
6,59 GiB, swap процесса достиг 130,5 MiB. У PTQ максимальный RSS был около
5,80 GiB, swap около 56 MiB, дополнительные чтения после загрузки — малые.
Во время PQ2 лимит CPU 3 снижался до 1,6512 ГГц; к завершению датчик достиг
65,9 °C. У PTQ также был троттлинг. Отделить вклад памяти от нагрева
по этой паре нельзя, однако оснований заменять установленный PTQ1 на PQ2
для генерации эти измерения не дают.

Отдельный сервер с PQ2, этим ARM-патчем и контекстом 512 также ответил
ровно `BONSAI_OK`: 23 входных и 6 выходных токенов, около 33,1 с на запрос.
Проверка подтверждает работоспособность конкретного ответа; она не заменяет
оценку качества на длинном контексте. Небольшая разница порядка float32
суммирования между ядрами остаётся возможной при точном совпадении весов.

Предшествующий CPU-контроль для GPU случайно получил декартово произведение
повторённых CLI-параметров: `llama-bench` добавляет варианты, а не заменяет
предыдущее значение флага. После четырёх завершённых строк процесс остановлен;
этот запуск помечен в JSON как исключённый. Для таблицы выше параметры
исправлены, каждая команда выполняет ровно два задания.

### Vulkan: операции работают, ограничения драйвера сохраняются

Собрана отдельная статическая Android arm64-версия Prism с Vulkan,
NDK 28.2, `-O3`, `armv8.2-a+dotprod+fp16`, без OpenMP. Установленный APK
не заменялся. Драйвер сообщил UMA, FP16 и отсутствие integer dot product /
matrix cores. Сначала проверялся исходный commit, затем только два файла
[PR #252](https://github.com/PrismML-Eng/llama.cpp/pull/252), head
`76798f98d2512d85339cf1f659d035df8621df4c`.

### Полная модель на GPU

Отдельная копия PTQ1 в `/data/local/tmp` проверена по SHA-256. Во всех
завершённых GPU-вариантах FlashAttention выключен. CPU-помощники: четыре
потока с маской 3–6; все слои, KV и поддерживаемые операции перенесены
на GPU. `llama-bench`, `-b 256`, один измеряемый образец после warmup.

| Вариант | Промпт / microbatch | Prefill, ток/с | Decode 16, ток/с |
|---|---|---:|---:|
| Vulkan baseline | 16 / 128 | — | — |
| Vulkan baseline | 1 / 1 | 0,279 | 0,245 |
| Vulkan + PR #252 | 1 / 1 | 0,588 | 0,576 |
| Vulkan + PR #252 | 16 / 4 | 0,841 | 0,687 |

Первый вариант завершился `ErrorDeviceLost` в прогреве промпта. Microbatch 1
позволил baseline завершить тест. PR #252 в сопоставимой паре дал примерно
2,35× скорости GPU decode; это одиночная пара, не точная устойчивая оценка.
Prefill с microbatch 4 также работает. Изменение decode между двумя
PR-запусками нельзя приписывать microbatch: отличаются прогрев и температура.
Во время нагрузок вычислительные датчики достигали 53–62 °C.

В одном полном GPU-запуске системный `GpuTotal` достиг 5,41 GiB, а RSS
процесса был менее 0,83 GiB. Поэтому оценивать память GPU-версии только
по `VmRSS` неверно. Минимальный `MemAvailable` — около 1,49 GiB; swap
самого процесса — около 54 MiB по снимкам. Это не гарантия работы при
контексте 4096 и фоновых приложениях.

Дополнительно проверены восемь GPU-слоёв при четырёх CPU-потоках,
`-ub 4`, промпте 16 и decode 16. Первый запуск дал 0,955 / 0,745 ток/с,
но зафиксированы ошибки affinity, поэтому он исключён из чистого сравнения.
Повтор с тем же PR #252 и патчем affinity прошёл с масками CPU 3, 4, 5, 6:
**0,889 ток/с prefill и 0,744 ток/с decode**. Это также не демонстрирует
выигрыша над ранее измеренным CPU с пятью быстрыми ядрами.

Отдельный `llama-server` с PR #252, контекстом 512 и `-ub 4` вернул ровно
`BONSAI_OK` на запрос с отключённым thinking. Запрос занял около 41 с;
это проверка одного ответа, а не полноценная проверка качества.
Полные ответы, server timings, параметры и сырые снимки сохранены
в JSON-отчёте. На данный момент CPU остаётся более быстрым измеренным
вариантом генерации; GPU-кандидат в APK не включён.

## Что видно в коде

### PTQ1_0: SIMD уже работает, специализированного ARM GEMM нет

В GGUF 402 тензора PTQ1_0, 96 BF16 и 353 F32. На PTQ1_0 приходится
26 869 760 000 параметров. Ширины строк PTQ1_0: 5120, 6144 и 17408.
В рабочем варианте общей CPU-маски на PTQ dot product пришлось 89,38%
выборок пользовательского CPU-времени. Это обоснованное место для следующей
оптимизации; сам профиль символов не разделяет вычисления и ожидание памяти.

CPU выбирает `ggml_vec_dot_ptq1_0_q8_0`, `vec_dot_type=Q8_0`, `nrows=1`.
Это общий C-код с распаковкой 128 троичных весов и четырьмя масштабами
активаций Q8_0. Отдельной реализации PTQ1_0 в `arch/arm` и ARM-пути repack
в этом коммите нет. PTQ1_0 также отсутствует в диспетчере llamafile SGEMM.
Обработка промпта поэтому повторяет dot product для каждой пары строки
весов и строки активаций; распаковка весов повторяется для разных токенов.

Однако Clang уже преобразовал общий код в NEON: в объекте установленной
сборки обнаружены **8 инструкций `sdot` на цикл из 128 весов**. Буфер
`q[128]` из C-кода не материализован как массив на стеке в этом цикле.
Называть текущую реализацию полностью скалярной было бы ошибкой.
Дизассемблирование сохранено в `build/device-bonsai/ptq1-arm.asm`.

Практический кандидат: матричное ARM-ядро, которое распаковывает блок один
раз для нескольких токенов/выходов, и оптимизация распаковки/накопления
для одиночного токена. Это требует измерений и проверки численной точности.
Одного добавления `+dotprod`, `-O3` или включения repack недостаточно:
эти параметры уже включены.

Источники: [CPU dispatch](https://github.com/PrismML-Eng/llama.cpp/blob/842b1880415d6f508f03b789e5ce70194def7bfd/ggml/src/ggml-cpu/ggml-cpu.c),
[общая распаковка и dot product](https://github.com/PrismML-Eng/llama.cpp/blob/842b1880415d6f508f03b789e5ce70194def7bfd/ggml/src/ggml-cpu/quants.c),
[repack dispatch](https://github.com/PrismML-Eng/llama.cpp/blob/842b1880415d6f508f03b789e5ce70194def7bfd/ggml/src/ggml-cpu/repack.cpp).

### PQ2_0: микробенчмарк выявил разницу между ARM-путями

Официальный PQ2_0 хранит те же троичные веса в более простой упаковке.
Файл занимает 7,21 GB против 5,95 GB у PTQ1_0: примерно **+1,26 GB**.
В опубликованных Prism тестах GPU PQ2_0 быстрее обрабатывает промпт;
эти результаты не являются измерениями Snapdragon.
[Карточка модели](https://huggingface.co/prism-ml/Ternary-Bonsai-2-27B-gguf).

В закреплённом исходнике есть ручное NEON-ядро `PQ2_0 × Q8_0`, однако
обычный CPU dispatch выбирает `PQ2_0 × Q8_K`. На ARM последняя функция
использует общий C-код. Q8_0 выбирается лишь при ширине строки, не кратной
256; все найденные ширины данной модели кратны 256. Repack для PQ2_0
в этом коммите выбирается только на AVX-512/VNNI.

Сравнение ядер выше подтвердило преимущество ручного Q8_0 над стандартным
Q8_K. Эксперимент с полной моделью и ARM dispatch на Q8_0 описан выше;
его результат не оправдывает замену PTQ1 на этом телефоне. По сравнению со стандартным PQ2 меняется квантование активаций
(у исходного PTQ уже используется Q8_0),
так что нужна проверка ответов/точности. Более крупные веса также могут
ухудшить ситуацию с памятью на телефоне с 12 GB RAM. Установленный PTQ1_0
в одном снимке процесса занимал около 5,75 GiB RSS; это не пик всей системы.

Источники: [ARM PQ2_0](https://github.com/PrismML-Eng/llama.cpp/blob/842b1880415d6f508f03b789e5ce70194def7bfd/ggml/src/ggml-cpu/arch/arm/quants.c),
[выбор fallback](https://github.com/PrismML-Eng/llama.cpp/blob/842b1880415d6f508f03b789e5ce70194def7bfd/ggml/src/ggml-cpu/arch-fallback.h).

### CPU-патч Prism #249

[Prism PR #249](https://github.com/PrismML-Eng/llama.cpp/pull/249) меняет
разделение работы при квантовании активаций: строку готовит один поток,
что устраняет совместную запись соседних участков кэш-линий несколькими
ядрами. Текущий PTQ1_0 проходит через изменяемый участок кода.
На дату исследования патч ещё не объединён; автор измерял Xeon и прямо
указывает, что ARM и неоднородные ядра не проверены.

Для локального опыта использована версия PR
`6d1d921ddd97e715a98d499738e967e8ff85215e`. На обе сравниваемые сборки
добавлен одинаковый патч повторной affinity, чтобы исключить наблюдавшиеся
ошибки старта. Первый decode-образец PR #249 — 0,977 ток/с против 0,896
у предыдущего запуска без #249. Однако чтение с накопителя отличается
(4,6 MB против 1,37 GB), а тепловое ограничение после теста — 1,98 против
1,59 ГГц. Контрольный повтор без #249 дал 0,973 ток/с, практически столько
же: разница с #249 составляет 0,45%. Воспроизводимого выигрыша decode
от #249 на этом телефоне не установлено. Prefill и численная точность
этого PR отдельно не сравнивались.

### Реализация привязки есть, но её результат нужно проверять

PI DECK передаёт пять быстрых ядер для decode и восемь ядер для batch,
с отдельными строгими масками. В Prism Linux-реализация affinity включает
Android, а `common_init_result` создаёт и подключает оба thread pool.
Два старых патча PI DECK для b10092 здесь повторять не требуется.
Однако проверка `/proc` и профилирование выше обнаружили отказ отдельного
вызова строгой привязки; наличие реализации само по себе не гарантирует,
что каждый поток получил запрошенное ядро.

Сравнение 3/4/5 потоков приведено выше. Число потоков нужно оценивать вместе
с их фактическим размещением: срыв распределения оказался сильнее различий
между исправно работающими конфигурациями. Текущие параметры приложения —
пять потоков decode, восемь batch, `-ub 128`, `-b 256`.

Источник: [создание thread pools](https://github.com/PrismML-Eng/llama.cpp/blob/842b1880415d6f508f03b789e5ce70194def7bfd/common/common.cpp).

## GPU и NPU

| Вариант | Состояние для этой модели | Следующее действие |
|---|---|---|
| Vulkan / Adreno 740 | Изолированная сборка запускает Bonsai при `-fa off`, малом microbatch; GPU decode пока медленнее CPU | Не включать в APK по этим результатам; устранение FlashAttention / больших пакетов требует дальнейшей работы |

| Hexagon NPU | PTQ1_0/PQ2_0 отсутствуют в поддерживаемых типах matmul | Включение backend само по себе не ускорит основные матрицы |

На этом же телефоне Vulkan b10333 ранее аварийно завершался при создании
Q6_K/Q4_K/Q8_0 pipelines, затем FlashAttention; обходы не дали рабочего
decode. Это была другая модель и другой runtime. Новые Prism-ядра дают
основание для повторной проверки. В текущем опыте PTQ1/BF16 работают,
но FlashAttention снова не создаёт pipeline; полный запуск стал возможен
при `-fa off` и малом microbatch.
[Результаты прежнего Vulkan-теста](performance.md#vulkan-on-adreno-740-measured-and-rejected).

оптимизирует float/dequant путь PTQ1_0 Vulkan. Описанный автором прирост
около 3× получен на AMD с принудительным выбором этого пути. При работе
integer-dot ядра автор не подтвердил выигрыш. В нашем Adreno-тесте
integer dot недоступен, а PR улучшил decode с 0,245 до 0,576 ток/с
в одиночной паре запусков; деталей и ограничений это не отменяет.

## Как уменьшить ожидание ответа

- Использовать Chat для обычного диалога: короткий системный промпт уже
  предусмотрен; агентные схемы инструментов увеличивают prefill.
- Сохранять работающий сервер между репликами и проверять реальные
  `cache_n`/`prompt_n`. Расширение истории разрешает `cache_prompt`, но
  изменение шаблона или списка инструментов может потребовать повторного
  вычисления. Одно разрешение кэша не доказывает попадания в него.
- Thinking уже отключён профилем. Сокращение требуемого ответа уменьшает
  время ожидания, сохраняя прежнюю скорость генерации токенов.
- Проверять частоты, температуру, major faults и давление на память.
  На SM-S918B уже измерены сильные потери из-за нагрева и изменения
  CPU-set при уходе приложения с переднего плана. В текущих запусках Bonsai
  лимит большого ядра снижался до 47–66% номинала; отдельный
  коэффициент потери скорости только от нагрева здесь не установлен.
  [Предыдущие наблюдения](performance.md#two-ways-this-device-gets-slower-measured-2026-07-29).
- Не переносить рекомендацию `--cache-ram 24576` из настольного demo на
  телефон с 12 GB RAM. Текущий лимит — 256 MiB. Размер KV и лимит prompt
  cache нужно менять только после измерения памяти и повторной обработки.

В данном GGUF нет MTP/NextN тензоров и соответствующего параметра слоёв.
Включение MTP требует совместимых дополнительных весов. Для отдельной
draft-модели нужно учитывать память, долю принятых токенов и цену проверки
основной моделью; при медленном prefill ускорение не гарантировано.
Upstream также отмечает неработающий `ngram-*` для этой модели.
[Известные ограничения Prism](https://huggingface.co/prism-ml/Ternary-Bonsai-2-27B-gguf/blob/main/KNOWN_ISSUES.md).

## Что делать дальше

1. Проверить повторную привязку в процессе приложения: маски обоих пулов,
   несколько стартов, уход с переднего плана и возврат. Сохранить строгую
   привязку и диагностировать исчерпание повторов. Переход на общую маску
   сам по себе не решил наблюдавшиеся провалы.
2. Измерить release APK через Pi: холодный запуск, несколько реплик с
   повторным использованием prompt cache, длинный ответ и отмена. Включить
   обычный контекст 4096; записывать TTFT, prefill, decode, RSS, частоты и
   page faults. Замеры shell-процесса не заменяют эту проверку.
3. Сохранить PTQ1 на этом телефоне. PQ2 с ручным ARM-ядром имеет смысл
   повторно оценивать при большем запасе RAM и контролируемом тепловом
   режиме; текущий полный тест показал ухудшение генерации.
4. Для PTQ1 исследовать ARM GEMM, который переиспользует распаковку между
   токенами. Испытанная замена скалярного накопления на 1/2/4 NEON-вектора
   выигрыша не дала; повторно включать уже работающий SIMD смысла нет.
5. Vulkan оставить экспериментом: проверенные малые пакеты работают,
   FlashAttention и большие пакеты имеют ограничения драйвера, а быстрого
   GPU decode относительно CPU пока не получено. OpenCL, Hexagon и MTP
   требуют дополнительных реализаций или весов, перечисленных выше.

Главные подтверждённые результаты — влияние фактического размещения
потоков, различие стандартного и ручного PQ2-ядра на ARM и улучшение
Vulkan PTQ-пути патчем #252. Готового постоянного ускорения над правильно
работающим CPU-вариантом эти новые опыты пока не дали.

## Состояние после экспериментов

Временные модели и 13 тестовых программ удалены с телефона. Исходный GGUF
в Downloads и приватная копия приложения сохранены; настройка бодрствования
восстановлена в исходное значение 2. Тестовые процессы остановлены,
ADB-forward отсутствуют, PI DECK возвращён на передний план.
SHA-256 release APK и упакованного CPU runtime совпадают с исходными.
Кандидаты, патчи, исходники проб и локальная перепакованная модель остались
в рабочем каталоге для воспроизведения; в приложение они не включены.

## Дополнительная проверка: смешанный PTQ1/PQ2

По следующей гипотезе перепакованы только 64 матрицы `blk.*.ffn_down.weight`:
это **5 704 253 440 троичных весов**, или 21,23% от PTQ-части модели.
Размер смешанного файла **6 214 035 808 байт** (+267 386 880 к PTQ1).
При конвертации проверен каждый преобразованный трит и FP16-масштаб;
невыбранные тензоры скопированы без изменения. SHA-256 созданного на телефоне
GGUF: `1c86affab35cdfe4daf13ca2aa7ea7da5b7e4a62fec2eea7915cbebf21233290`.
Воспроизводящие файлы: [выбор тензоров и заголовок](../benchmarks/out/bonsai2-mixed-ffn-down-2026-09-24.py),
[конвертер](../benchmarks/out/bonsai2-pq2-repack-2026-09-24.cpp),
[полный протокол](../benchmarks/out/bonsai2-mixed-ffn-down-sm-s918b-2026-09-24.json).

Одна и та же экспериментальная сборка Prism с ARM PQ2×Q8_0 и повторной
попыткой affinity измеряла оба файла. Параметры: CPU 3–6, четыре потока,
`-dev none -ngl 0 -b 256 -ub 4 -p 16`; каждый прогон включал прогрев и
один измеряемый образец. Перед стартами телефон возвращался к максимальной
частоте большого ядра 3,36 ГГц. Замеры ниже относятся к отдельному shell
процессу, а не к release APK с контекстом 4096.

| Порядок, 32 выходных токена | Prefill, ток/с | Decode, ток/с |
|---|---:|---:|
| PTQ1 A | 0,972 | 0,879 |
| Смешанный A | 1,185 | 0,942 |
| Смешанный B | 1,075 | 0,864 |
| PTQ1 B | 0,856 | 0,661 |

Обе короткие пары благоприятны для смешанного файла: prefill +22–26%,
decode +7–31%. Разброс decode велик, поэтому эти проценты не следует
переносить на длительный ответ. В одном повторе смешанный процесс достиг
6 177 084 KiB VmHWM и 57 780 KiB VmSwap, PTQ1 — 6 082 732 KiB
и 0 KiB соответственно; это снимки отдельных процессов, а не полной памяти
системы.

| Порядок, 64 выходных токена | Prefill, ток/с | Decode, ток/с |
|---|---:|---:|
| PTQ1 | 0,867 | 0,514 |
| Смешанный | 0,800 | 0,493 |

В более длинной паре выигрыш не сохранился: смешанный вариант ниже на 7,7%
по prefill и на 4,2% по decode. Начало смешанного запуска было теплее
(AP 45,6 °C против 43,7 °C), во время него частотный лимит снижался до
1,59 ГГц, а swap достигал 65 MiB. У PTQ1 лимит тоже падал до 1,98 ГГц.
Из двух запусков нельзя отделить влияние формата, температуры и памяти.
В двух промежуточных снимках смешанного процесса `read_bytes` изменился
лишь примерно на 0,3 MiB, то есть явного повторного чтения гигабайтов,
замеченного у полного PQ2, в этом промежутке не было.

Сервер со смешанным GGUF ответил `BONSAI_OK` на тестовый запрос при
отключённом thinking. Это проверка работоспособности, не оценка качества
модели. **Оснований менять PTQ1 в release APK пока нет:** ускорение коротких
прогонов не повторилось на более длинной генерации. Для решения об установке
нужны длительные парные тесты при близкой температуре и в реальном приложении.
По решению пользователя смешанный PQ2 остаётся **приоритетным экспериментальным
кандидатом** среди проверенных способов ускорения, несмотря на пока
неподтверждённый выигрыш при длительной генерации.

## Проверка кэша промпта в установленном APK

24 сентября на SM-S918B после восстановления старой зависшей операции
создана новая Pi RPC session без replay. В Chat с запущенным PTQ1 отправлены
три короткие последовательные реплики с однословными ответами. Сервер между
репликами не перезапускался; счётчик контекста вырос с 78 до 98 и 118 токенов.
Время ограничено снимками экрана, поэтому это интервалы, а не точный TTFT.

| Реплика | Ответ ещё отсутствовал через | Ответ уже виден через | Завершение не позднее |
|---|---:|---:|---:|
| 1, новая сессия | 59 с | 87 с | 131 с |
| 2, продолжение | 59 с | 118 с | 118 с |
| 3, продолжение | 48 с | 95 с | 95 с |

Последовательное время полного ответа уменьшилось, но по этим границам
нельзя приписать сокращение именно кэшу. Во время серии Android thermal
status был 1, AP 58–59 °C, а лимит большого ядра составлял около 2,34
вместо 3,36 ГГц. Установленный APK не debuggable, поэтому его приватный
native-log с `cache_n`/`prompt_n` через `run-as` недоступен. Эффект кэша в
реальном приложении остаётся неподтверждённым.

После восстановления ADB проведена отдельная контрольная серия с тем же
PTQ1 на сервере той же сборки Prism. У сервера было по одному слоту,
контекст 512, пять вычислительных потоков на CPU 3–7, batch-потоки на
CPU 0–7. Каждый ответ содержал два выходных токена. До серии thermal
status был 0, AP 37,9 °C, лимит большого ядра 3,36 ГГц.

| Запрос | `cache_prompt` | `cache_n` | `prompt_n` | Полное время |
|---|---:|---:|---:|---:|
| Первый | false | 0 | 16 | 11,68 с |
| Точный повтор | true | 12 | 4 | 4,73 с |
| Точный повтор, контроль | false | 0 | 16 | 12,72 с |
| Растущая история | true | 17 | 18 | 16,09 с |
| Та же история, контроль | false | 0 | 35 | 29,65 с |
| Та же история, повтор | true | 31 | 4 | 4,84 с |

Кэш движка работает: для растущей истории он сократил полное время на
45,7% относительно запроса без кэша, для точного повтора — на 62,9%.
Это парные короткие запросы к отдельному серверу, а не измеренный выигрыш
установленного APK. Приватный native-log release APK остаётся недоступным,
поэтому в приложении фактический `cache_n` пока не подтверждён.
[Полный JSON](../benchmarks/out/bonsai2-prompt-cache-sm-s918b-2026-09-24.json).

## Парное ARM-ядро PTQ1 для предзаполнения

На SM-S918B проверен следующий вариант: декодировать блок PTQ1 один раз и
применять его к двум входным токенам через NEON SDOT. Для эксперимента
собрана отдельная версия Prism/ggml; установленный APK не менялся.
Проверка `nrc=2` против четырёх исходных скалярных произведений дала нулевое
расхождение на 64 строках (32 парах) для ширин 5120, 6144 и 17408. Диагностическая
сборка подтвердила, что путь `nrc=2` вызывается при предзаполнении Bonsai 2.

| Токенов на один распакованный блок | Ускорение отдельного умножения |
|---:|---:|
| 2 | 1,45× |
| 4 | 1,98× |
| 8 | 2,25× |

Это медианы четырёх чередующихся пар на одном ядре CPU 3. В ggml пока
подключён только вариант для двух токенов. Для полной модели с 32 входными
токенами, пятью потоками на CPU 3–7, без GPU и без прогревочного прохода:

| Состояние страниц модели | Исходное ядро | Новое ядро |
|---|---:|---:|
| Первые прогоны, чтение 3–6 ГБ | 1,121 токена/с | 1,114 токена/с |
| Поздние прогоны | 1,290 токена/с | 1,696 токена/с |

В поздней паре новое ядро оказалось быстрее в **1,32 раза**, хотя его процесс
прочитал ещё 2,3 ГБ с накопителя, а исходный — лишь 0,01 ГБ. Дополнительный
диагностический прогон нового ядра показал 1,817 токена/с при чтении 0,97 ГБ.
Значительный и непостоянный I/O не позволяет считать 1,32× точной оценкой
ускорения вычислений или работы в APK. При повторной проверке протокола
обнаружена ещё одна помеха: в `patched-a` один поток сохранил маску `0–7`
вместо отдельного CPU 5; в `baseline-a` аналогично не закрепился поток CPU 6.
Поэтому первую пару нельзя объяснять только чтением с накопителя. В поздней
паре `baseline-c` / `patched-b` снимки показывают пять отдельных CPU 3–7.
По окончании серии ADB отключился, поэтому заключительный
контроль и очистка временной копии модели ожидают повторного подключения.
[Исходный патч](../benchmarks/out/bonsai2-ptq1-tile-arm-2026-09-24.patch) и
[результаты](../benchmarks/out/bonsai2-ptq1-tiled-arm-sm-s918b-2026-09-24.json).

## Повторная проверка PTQ1 ARM — 25 сентября

После восстановления ADB проведены четыре запуска в порядке «обычный,
парный, парный, обычный». Обе сборки используют один pinned commit и один
патч повторной привязки; только кандидат дополнительно содержит парное
PTQ1-ядро. SHA-256 модели на телефоне совпала с исходной. Повторная проверка
`nrc=2` на 64 строках шириной 5120, 6144 и 17408 снова дала нулевую ошибку.

Параметры: пять потоков, строгая маска CPU 3–7, CPU без offload, mmap,
`-b 256 -ub 128 -p 32 -n 0 -r 1`, стандартный прогрев перед измерением.
Перед каждым стартом лимит большого ядра был 3,36 ГГц, а максимальная
температура вычислительных датчиков — 41,4–42,6 °C. Каждые две секунды
снимались память, I/O и маски всех потоков. Во всех снимках с пятью потоками
они занимали пять отдельных CPU 3–7. В `tile-a` и `base-b` понадобилось
по одной успешной повторной попытке affinity.

| Порядок | Prefill, ток/с | Прочитано, GiB¹ | Максимальный swap, MiB¹ |
|---|---:|---:|---:|
| Обычный A | 1,177 | 10,30 | 189,7 |
| Парный A | 1,715 | 1,92 | 199,5 |
| Парный B | 1,830 | 0,48 | 179,0 |
| Обычный B | 1,201 | 1,99 | 122,2 |

¹ По снимкам процесса, включая загрузку и прогрев; последний снимок
не равен точному счётчику при завершении процесса. Кэш страниц не сбрасывался
и не закреплялся в памяти. Стандартный прогрев не устранил разницу в I/O.

Парное ядро быстрее в обеих парах: **1,46× и 1,52×**. Неисправная привязка
потоков в этой серии исключена по снятым показаниям. Однако у кандидата
меньше чтения с накопителя в обеих парах, а в конце последнего контроля
лимит частоты упал до 2,48 ГГц. Поэтому эти коэффициенты описывают данные
четыре запуска, а не чистое ускорение ядра или гарантированный выигрыш APK.
Преимущество короткого prefill повторилось; влияние на генерацию и работу
приложения ещё не измерено.

[Полный протокол с командами, хешами, масками потоков и снимками памяти](../benchmarks/out/bonsai2-ptq1-repeat-sm-s918b-2026-09-25.json).
Локальные сырые логи: `build/device-bonsai/measurements/ptq1-review-*`.
Проверки Python: 58 tooling и 129 runtime тестов прошли; задачи Gradle
`testDebugUnitTest`, `verifyNativeRuntime`, `verifyModelManifest` завершились
успешно (результат Java unit tests использован из актуального кэша).
Чтение температур через shell builtins дополнительно покрыто тестом без
внешних команд, включая недоступные и некорректные датчики.

APK не переустанавливался, production runtime не менялся. Настройка
бодрствования восстановлена в 2. Временная копия модели и экспериментальные
утилиты сохранены на телефоне для дальнейшего сравнения; их очистка остаётся
отдельным незавершённым пунктом предыдущей серии.

## Кандидаты для реализации

По выбору пользователя в список будущих улучшений входят:

1. **Смешанный PTQ1/PQ2** — приоритетный экспериментальный кандидат.
   Перед включением в APK нужен устойчивый выигрыш на длинной генерации.
2. **Повторное использование prompt cache** — подтвердить `cache_n` в
   release APK, затем устранить причины сбросов там, где история и шаблон
   действительно остаются одинаковыми. Выигрыш движка на растущей истории
   уже измерен выше.
3. **Парное PTQ1-ядро ARM для предзаполнения** — перенести проверенный
   `nrc=2` путь в движок приложения после повторных замеров с контролируемым
   I/O; оценить ускорение именно в APK. На генерацию по одному токену этот
   вариант сам по себе не влияет.
