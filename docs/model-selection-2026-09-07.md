# Модель для PI//DECK: проверка на SM-S918B, 7 сентября 2026

Запрос: релизы августа–сентября 2026, обычные агентские задачи и программирование, минимум 8–10 токенов/с. Проверка проведена на подключённом Samsung SM-S918B, Snapdragon 8 Gen 2, 12 GB RAM. Выводы относятся к этому телефону и указанным артефактам.

## Выбор по полученным данным

**K2 Horizon 3.7B Q4_K_M — наиболее перспективный новый кандидат для сочетания программирования и обычных инструментов.** На собранном Android CPU runtime с i8mm получено **9,23 ток/с**, три измерения **9,20–9,32**, после отдельного прогрева. В этой серии средняя скорость выше 8 ток/с и ниже 10. В отдельном коротком запросе после исправления парсера наблюдалось **7,35 ток/с**, поэтому гарантированный нижний порог 8 ток/с не подтверждён. В компактном тестовом агенте модель прошла чтение отсутствующего файла, исправление кода с выполнением четырёх проверок и вызов погоды.

Это **экспериментальный кандидат, не допуск в автоматическую рекомендацию PI//DECK**. Компактный исполнитель инструментов работал на хосте, инференс — на телефоне. Полный Pi, разрешения приложения, многозадачные сессии, длинный контекст и длительная стабильность K2 ещё не прошли штатные admission gates. В исходной сборке обнаружен выход служебного тега рассуждения в ответ; подготовлен и проверен отдельный экспериментальный патч, описанный ниже.

**Для текущего приложения сохраняется LFM2.5 2.6B QAD — практическая быстрая база.** В свежих штатных задачах получено 14,05–16,87 ток/с, но надёжность программирования ограничена. Сам Liquid AI рекомендует эту модель для инструментов и общих агентских задач и отдельно не рекомендует для agentic coding. [Карточка модели](https://huggingface.co/LiquidAI/LFM2.5-2.6B).

Ни одна из проверок не даёт основания обещать одновременно стабильные ≥10 ток/с и надёжное выполнение произвольных задач программирования. Полная перепись приложения по имеющимся данным не обоснована.

## Что проверено в установленном PI//DECK

APK: `dev.pideck.app`, `0.3.0-alpha13`, versionCode 21. Активная модель — `lfm2.5-2.6b-qad`. Штатный путь: Android foreground service → llama.cpp → аутентифицированный локальный Python bridge → Pi 0.82.1 и TypeScript-инструменты в Termux.

| Задача Suite-v2 | Результат | Вызовы | Время задачи |
|---|---|---:|---:|
| Q01: точная строка без инструментов | pass | 0 | 26,90 с |
| Q04: отсутствующий файл, один `read` | pass | 1 | 48,87 с |
| Q03: найти определение функции | **fail по ограничению вызовов** | 5 `code_nav` | 137,53 с |
| Q10: веб-поиск | pass по формальным условиям набора | 1 | 88,55 с |
| Q11: выбор инструмента погоды | pass | 1 | 65,73 с |

В Q03 первый поиск уже нашёл нужное определение. Итоговый ответ верный, но модель продолжила поиск. Q10 проверяет URL и ограничение вызовов; это не полноценная независимая проверка фактической точности веб-ответа.

Диагностический Q05 в `confirm_changes` завершился неудачей за 413,17 с: неверные `line:hash`, затем повторение заблокированных вызовов. Файлы не изменились. Этот прогон **нельзя считать каноническим admission-тестом**: `run_tests` намеренно отсутствует в этом профиле. Штатный Suite-v2 требует `autonomous` для задач с изменением файлов; В каноническом профиле `autonomous` Q05 затем **прошёл** за **194,67 с**, с шестью вызовами: ошибочная правка, три отклонённых чтения, успешная правка и `run_tests`. Изменился только `src/counter.py`; тест прошёл. Ответ модели был на английском. Это подтверждает восстановление после ошибки, но показывает большую задержку.

Q06 (переименование метода и обновление второго файла) **не прошёл**: девять `read`, все отклонены, **300,48 с**, ни одного изменения. Harness остановил задачу только после превышения установленного Suite-v2 лимита в восемь вызовов. Итог штатной проверки программирования: **1/2**, сохранность остальных файлов и внешнего sentinel подтверждена.

Одна ранняя попытка остановилась из-за idle timeout: прямой bridge-harness не уведомляет Android UI о начале инференса. Её не учитываем как ошибку модели. Для последующих тестов таймер временно отключался.

## Компактный агент: смысл результатов

Исполнитель предоставлял только `read`, точную текстовую замену `edit`, `run_tests` и `weather`. Файлы синтетические, правка ограничена арифметической функцией; тест действительно исполнял четыре проверки границ. Погода — явно обозначенная синтетическая фикстура.

K2 выполнила исправление за **35,09 с** и три вызова. LFM выполнила аналогичное исправление за **60,92 с инференса** и четыре вызова, включая повторное чтение. Это поддерживает гипотезу, что простой интерфейс правки полезнее малой модели, чем сложные якоря. Это не контролируемая оценка ускорения: различаются токенизатор, runtime, параметры и состояние кеша.

В исходном компактном прогоне LFM поле `seconds` включало охлаждение, а первый запрос следующей задачи допускал повторное использование префикса. В аннотированном JSON отдельно посчитано время запросов. Для дальнейших прогонов harness исправлен: новый кейс начинает с `cache_prompt=false`, повторное использование разрешено только внутри растущей истории кейса. Для гибридных моделей этот сброс существенен.

## K2: сборка и происхождение

Релиз K2 Horizon — **3 сентября 2026**. Название 3.7B относится к основной части модели; полный объём весов — около **5,06B параметров**. Нельзя планировать память как для обычной dense 3.7B. В измеренной конфигурации пиковый RSS около **5,3 GiB**. [Релиз IFM](https://ifm.ai/k2/press-release/), [официальная карточка](https://huggingface.co/IFM/K2-Horizon-3.7B).

- Runtime: `MBZUAI-IFM/llama.cpp`, ветка `model/K2Horizon`, commit `35999d101cf2233fc54f09c3c8d599da7303ce02`.
- Android NDK `28.2.13676358`, arm64, API 28, Release, статическая CPU-сборка; `armv8.6-a+dotprod+fp16+i8mm`.
- Контекст 8192, decode/batch 5/5 потоков, маска 3–7 без строгого закрепления каждого потока, `poll=0`, batch 512, ubatch 128, CPU без offload.
- GGUF: сторонний `NANI-Nithin/K2-Horizon-3.7B-GGUF`, revision `6b8f11e53bd89304a715ba7b6cffb37589d90834`, `K2-Horizon-3.7B-Q4_K_M.gguf`, 3 156 598 464 байта.
- SHA-256 весов: `f8dce940ec3e45be3e884a203b0eb3dee4ba57eb23fc63d0e210cdade2ca48ec` — проверен на телефоне.
- SHA-256 runtime для серии скорости: `ad64e48f9b066ea6705fa4d4b95b4a5601e1460a5c7f143d43e60a259926a33c`.

Первый вариант сборки без i8mm с раздельными строгими пулами 5/8 не завершил запрос за 360 с. Это сбой испытанной конфигурации, не валидный замер скорости K2. Упрощённый 32-токенный диагностический запрос без affinity дал 7,67 ток/с. После смены сборки и конфигурации получена полная серия 9,23 ток/с. Влияние каждого изменения отдельно не изолировалось.

Официальные GGUF IFM на момент проверки предлагали BF16. Использованный Q4 — сторонняя конверсия; полный воспроизводимый provenance отсутствует. Также при сборке vendor runtime наблюдалась загрузка UI-артефакта `latest`, хотя сервер запускался без UI. Перед production нужна отдельная фиксация всех входов сборки. Хеширование готового бинарника не заменяет эту работу.

## Исправление формата K2

Автоматический анализатор vendor runtime выводил `</ifm|think_faster>` в пользовательский текст. Серверные `--reasoning-effort low --reasoning-format deepseek` проблему не устранили. Причина в шаблоне: сохранённое `reasoning_content` использует тег `ifm|think`, а префикс генерации low/medium открывает `ifm|think_faster` / `ifm|think_fast`.

Подготовлен [патч](../benchmarks/out/model-selection-2026-09-07/k2-reasoning-effort.patch): анализатор выбирает тег по реально открытому префиксу текущего запроса. Сам промпт не переписывается. Патч ограничен шаблонами IFM и применён только к экспериментальной vendor-копии, не к штатному runtime приложения.

Бинарник с патчем собран и проверен на телефоне: **один `read`, затем чистый русский ответ без служебного тега**. SHA-256: `a5fa3f2116f7c7a48b7882c449f302ee7411b73d26fce41beb36f5db2c0b095d`. [Результат проверки](../benchmarks/out/model-selection-2026-09-07/k2-parser-fixed.json).

Это проверка одного low-effort кейса, не полная регрессия high/medium, reasoning cap, streaming и всех инструментов. Скорость двух коротких запросов — 7,35 и 8,52 ток/с. Повторной серии из трёх 192-токенных прогонов на этом бинарнике нет; медиана 9,23 относится к исходной i8mm-сборке. Отдельные короткие запросы нельзя напрямую сравнивать с такой серией или приписывать разницу только патчу.

## Что имеет смысл менять в приложении

1. Для K2 нужен отдельный runtime/profile с точным происхождением и корректным разбором IFM reasoning/tool формата. Подмена stock runtime для всех моделей не требуется.
2. Пересмотреть предварительную подгрузку файлов и запрет повторного чтения для LFM: сейчас prefetch уже отмечает файл прочитанным, а явные `read` модели отклоняются. Нужен измеренный вариант с одним разрешённым явным чтением и понятным результатом инструмента. Проверять простой редактор точной замены с существующими ограничениями путей, проверкой актуальности файла и разрешениями. Успех компактного `edit` ещё не даёт права ослаблять защиту штатного редактора.
3. Завершать агентский цикл после исчерпания допустимых попыток. Сейчас отказ инструмента защищает файл, но не останавливает повторные запросы модели и потерю времени.
4. Оптимизировать объём первого промпта, повторное использование контекста и число раундов. Decode 15 ток/с не предотвращает задержку ответа на 30–90 секунд.

В исходниках уже есть сентябрьские исправления affinity для b10092; установленный APK использует более старые stock-библиотеки. В нативных экспериментах использована совпадающая с исходниками сборка `pideck-affinity1`. Это разные runtime, их результаты не смешиваются. Предыдущие отчёты OpenCL/HTP не дали основания включать их вместо CPU для общего ускорения агента; новый полный accelerator sweep здесь не проводился.

На системном разделе при начале работы оставалось около 46 MB; это ограничивает нормальную сборку. Чужие файлы, модели и незавершённые изменения не удалялись.

[Все результаты аудита](../benchmarks/out/model-selection-2026-09-07/) содержат отдельные пометки для прежних измерений, диагностических режимов, загрязнённой нагрузки и прерванных кейсов.
