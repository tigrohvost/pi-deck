# Скорость, стабильность и модели до 5 ГиБ

Дата: 2026-08-10. Статус: одобрено, ждёт implementation plan.

## Проблема

Дека работает медленно на своём собственном устройстве (SM-S918B, Snapdragon
8 Gen 2, 12 ГиБ). Измеренные причины — четыре разных болезни
(`docs/performance.md`, `docs/model-throughput-survey.md`):

1. **Долгий первый токен.** Холодный старт ядра 20–29 с; replay сессии на 8k
   токенов — 173 с prompt-обработки до первого символа ответа.
2. **Decode упирается в память.** `tok/s ≈ 25.6 / GiB^1.2`: 10 tok/s ⇔ ~2.2 ГиБ
   весов. Плотная модель 5 ГиБ на этом CPU — 3–4 tok/s, вне интерактива.
3. **Термотроттлинг.** Часы инференса → big cores на 44 % клока, prompt
   processing падает на порядки. Деградация молчаливая.
4. **cpuset.** Любое чужое приложение на переднем плане → `/moderate` →
   ~1.5 tok/s. Возврат деки на передний план восстанавливает мгновенно.

Отдельно — стабильность: turn изредка застревает в busy/«…» (потерянный
HTTP-ack, поздние callbacks; часть механики уже в unreleased).

Цель пользователя: быстрее, стабильнее, модели до 5 ГиБ. Решения:
одобрен подход «эволюция llama.cpp» — новый пин + MoE + GPU-prefill,
резидентное ядро на время активной работы, полная свобода по замене
нативного runtime при условии прохождения существующих admission-гейтов.

## Критерии успеха

Все числа — SM-S918B, передний план, термоконтроль по методике
`tools/speculative_probe.py` (ожидание восстановления клока, headroom рядом с
каждой выборкой).

| Метрика | Сейчас | Цель | Гейт |
|---|---:|---:|---|
| TTFT, тёплое ядро, продолжение сессии | ~9 с | < 3 с | обязательный; при недостижимости — измеренная раскладка, где сидит время (prefill / Pi / bridge) |
| TTFT, холодный старт + 8k сессия | ~174 с | ≤ 90 с | prefill ≥ 2x, иначе GPU не шипится |
| Decode, MoE 4–5 ГиБ | — | ≥ 12 tok/s | ≥ 10 tok/s, иначе модель остаётся CANDIDATE |
| Decode, Qwen3.5 2B на новом пине | 13–18 tok/s | паритет ±5 % | обязательный для смены пина |
| Зависший turn | случается | 0 в смоках и induced-failure тестах | обязательный |
| Деградация в жаре | молчаливая | индикатор + опциональный pacing | UX-гейт |
| Фон `/moderate` | ~1.5 tok/s | измерить re-affinity, честный индикатор | эксперимент |

Принцип: каждый этап имеет измеримый гейт и путь отката; нет доказанного
выигрыша — изменение не едет.

## Этап 0 — стабильность turn'а

Фундамент: пока turn может застрять, любые бенчмарки длинных сессий
недостоверны.

- Turn-watchdog в `OperationCoordinator`: сконфигурированное время без токенов
  и без control-событий → сверка `/state` → fail-closed сброс busy с явной
  ошибкой в деке. Достраивает механику unreleased-фиксов (UNKNOWN до сверки,
  поздние callbacks заменённого child, потерянный HTTP-ack).
- Induced-failure тесты: убить Pi child посреди turn, оборвать HTTP-соединение,
  подавить terminal event — busy обязан сняться сам во всех случаях, кнопка
  отправки не остаётся в «…».

## Этап 1 — новый пин llama.cpp

Сам по себе новый билд скорости не даёт (контроль b10333 показал паритет);
он нужен как носитель MoE-кернелов LFM2-8B-A1B и зрелого OpenCL-бэкенда.

- Свежий официальный Android arm64 билд в `third_party`; bump проверки
  `build == "b10092"` в `app/build.gradle.kts` (verifyModelManifest / проверка
  нативного бандла), SHA-256 сверка как сейчас.
- Гейт: A/B на Qwen3.5 2B с термоконтролем — pp/tg паритет ±5 %, 10 смоков,
  session/abort/tool-тесты зелёные.
- Откат: b10092 остаётся в репозитории до закрытия этапа 3; откат — revert
  пина.

## Этап 2 — MoE-адмиссия LFM2-8B-A1B

Единственный найденный способ дать «крупную И быструю»: 4.41 ГиБ весов,
1.5B активных параметров, прогноз по envelope ~20 tok/s (по активным).
Лицензия LFM Open v1.0 уже в allowlist после LFM2.5-2.6B.

- `tools/pin_model.py` → `LiquidAI/LFM2-8B-A1B-GGUF` Q4_0, вендорская
  конверсия, иммутабельная ревизия, независимые байты и SHA-256.
- Первое устройство-измерение до всякой адмиссии: загрузка на новом пине,
  RSS-пик, decode/pp, поведение RAM guard на реальных числах.
- **Главный риск — RAM.** 4.41 ГиБ весов + KV + рантайм ≈ 5.5–6 ГиБ RSS при
  ~5 ГиБ MemAvailable в лучшем измеренном случае. MoE, у которого эксперты
  вытесняются в флеш, перечитывает их на каждом токене — это смерть, а не
  замедление. Гейт: измеренный RSS без свопа и без вытеснения + decode
  ≥ 10 tok/s. Провал — модель остаётся `CANDIDATE`-полкой, этап закрывается
  честным отчётом в `docs/model-throughput-survey.md`.
- Контекст подбирается из RAM-бюджета по измерениям, не заранее.
- Дальше стандартные гейты 4–7 админки: load/health/session/abort, suite-v1
  (28 задач), mutation-проверки, 10 чистых смоков. До прохождения — статус
  `CANDIDATE`, вручную выбираемый.

## Этап 3 — GPU-prefill (OpenCL, Adreno 740)

Атакует TTFT и replay напрямую: prompt processing — единственная фаза, где
GPU этого класса доказуемо помогает llama.cpp.

- Сборка нового пина с OpenCL-бэкендом; libOpenCL берётся dlopen'ом из
  системы, на устройствах без пригодного OpenCL — деградация в CPU-путь без
  падения.
- Probe с термоконтролем: pp и tg отдельно, несколько значений `-ngl`.
- Гейт: pp ≥ 2x при tg ≥ 0.95x от CPU-базы. Иначе флаг не включается,
  конфиг остаётся CPU-only, отчёт с числами остаётся в docs.
- Конфигурация per-model в `models-v2.json` через существующий механизм
  `serverArgs`; схема расширяется, парсеры (Java/Python/Gradle) остаются
  строгими к неизвестным критичным полям.

## Этап 4 — политика ресурсов

- **Keep-alive.** Ядро живёт между запросами активной сессии, гаснет по
  таймауту бездействия (настройка в ЯДРО, дефолт порядка 10 минут).
  In-memory KV между turn'ами — уже рабочая механика (`cache_prompt`),
  закрепляется политикой, а не случайностью. Дисковый slot-кеш не включается —
  причины измерены и записаны в `docs/performance.md`.
- **Термо.** Чтение thermal headroom между turn'ами → расширение
  существующего `addThermalNotice`: видимый индикатор деградации и
  опциональный pacing («передышка до восстановления клока») перед длинными
  turn'ами.
- **Фон.** Детект ухода процесса в `/moderate` → эксперимент: перестройка
  thread-affinity под фактически доступные ядра (`CpuProfile` уже
  параметризован cpuset'ами). Выигрыш измеряется; независимо от результата —
  честная индикация «фон = медленно» в нотификации foreground-сервиса.

## Обработка ошибок

Существующий принцип fail-closed сохраняется везде:

- неоднозначное состояние → `UNKNOWN` + сверка журнала/`/state`, не авто-retry;
- RAM guard отказывает до старта сервера, не после OOM; его ожидания
  обновляются измеренными, а не расчётными пиками;
- новые пути (watchdog, GPU-фолбэк, re-affinity) при любом сомнении
  откатываются к текущему поведению;
- смена пина не трогает механизм проверки SHA-256 нативного бандла.

## Тестирование

- Юнит: состояния watchdog, парсер каталога с новыми полями, StartupPolicy
  keep-alive, CpuProfile re-affinity.
- Существующие сьюты `tests/protocol`, `tests/runtime`, `tests/extensions`,
  Java-тесты — зелёные на каждом этапе.
- Устройство: probe-скрипты в `tools/` с термогейтом; 10 смоков на смену пина
  и на модель; suite-v1 для модели; induced-failure сценарии для watchdog.

## Вне скоупа

- Смена бэкенда на MNN — отклонена по измерениям 2026-08-07 (крах disk-cache,
  нерабочие GPU-пути, паритет не доказан на гейте cold-8k).
- Дисковый KV/slot-кеш — отклонён по измерениям (не ускоряет первый ход,
  ~175 МиБ на 8k).
- Спекулятивный decode — отклонён ранее (0.96–1.05x).
- Плотные модели > 2.2 ГиБ как рабочий профиль — вне интерактива по физике;
  остаются выбираемыми вручную (`CANDIDATE`), как Bonsai 27B.

## Порядок исполнения

Этапы 0 → 1 → 2 → 3 последовательны: пин раньше модели, модель раньше
GPU-флагов. Этап 4 зависит только от этапа 0 и может идти параллельно с 1–3.
