# PI//DECK: спецификация доработки производительности, агента и приложения

**Дата аудита:** 16 октября 2026 года.  
**Репозиторий:** `tigrohvost/pi-deck`.  
**Зафиксированная ревизия:** `43faa8b711a8d9ecf1d75b8ef86aa3fb0110ad61`, `main`, коммит от 17 сентября 2026 года.  
**Версия исходников:** `0.3.0-alpha15`, `versionCode 23`.  
**Референсное устройство:** Samsung SM-S918B / Galaxy S23 Ultra, 12 GiB RAM; дополнительные устройства допускаются только с отдельными результатами.  
**Назначение документа:** техническое задание на следующую итерацию существующего продукта, а не проектирование нового приложения с нуля.

## 1. Решение в одном абзаце

Сохранить архитектуру Android-owned inference + Termux + Pi и существующие защитные контракты. Главную оптимизацию перенести с «максимума токенов в секунду» на **время до полезного действия и до проверенного результата**. В первую очередь устранить ложные подтверждения успешности, задержки отмены старта и ненадёжную публикацию. Затем сделать управление контекстом зависимым от стоимости повторного prefill, сократить лишние агентные циклы и превратить экран диалога в удобное рабочее место с проектами, историей, изменениями и проверками. Смена backend, GPU и расширение каталога моделей — только после сравнительной приёмки.

## 3. Что уже сделано правильно и не должно быть потеряно

В текущем проекте уже существуют: app-owned foreground inference, аутентифицированный loopback, ограниченный набор расширений, operation UUID и защита от поздних результатов, восстановление состояния без скрытого повторного запроса, проверка моделей SHA-256 с приватной read-only копией, компактная поверхность инструментов, append-only schema в сессии, консервативный контроль prefix reuse, scoped prefetch, структурные чтения, точные hashline-правки, применение инструкций репозитория, ограниченные повторные вызовы, FAST/DEEP и ограничение reasoning, PLAN с реальным подтверждением Android. Streaming уже объединяет дельты и не пересоздаёт форматирование на каждый токен. [S01, S02, S04, S08, S09, S10, S13]

Поэтому в эту итерацию **не включать** задачи «впервые добавить кэш», «добавить streaming», «добавить планирование», «зафиксировать SHA моделей», «ограничить retry». Требуется улучшить конкретные существующие реализации.

**Инварианты:** локальный inference без скрытой отправки кода в облако; профиль доступа не расширяется решением модели; один владелец мутирующей операции; stale operation/approval не действует на новую операцию; неизвестный результат мутации не приводит к автоматическому повтору; приватная модель не заменяется непроверенным файлом; история Pi остаётся источником истины; отмена и ошибки не рисуются успешным завершением. Workspace нельзя называть OS sandbox: shell и тесты обладают правами пользователя Termux. [S01, S02]

## 4. Исходная производительность: правильная интерпретация

| Сценарий из репозитория | Результат | Ограничение интерпретации |
|---|---:|---|
| Qwen3.5 2B, warm TTFT, smoke 10.08.2026 | медиана 0,557 с, 10 warm samples | Не P95, не гарантия для длинного нового запроса |
| Qwen3.5 2B, cold TTFT, тот же smoke | медиана 64,31 с, 2 cold samples | Малая выборка; включены старт и обработка контекста |
| Qwen3.5 2B, 7 975 токенов старой сессии после холодного старта, 07.08.2026 | 174,27 с запрос; 173,14 с prefill | В этом запуске bottleneck — replay, а не decode |
| LFM2.5 2.6B QAD Q4_0, августовские короткие прогоны | 16,47 и 15,71 decode tok/s на 128/192 токенах | Не полный агентный benchmark и не sustained-гарантия |

Источник: [S01, S03]. Результаты разных моделей и сценариев нельзя объединять в один «средний TPS».

Модель времени задачи:

```text
T_task = T_queue + T_start_when_cold
       + Σ(T_prefill_uncached + T_decode + T_tool + T_protocol)
       + T_approval_wait
```

Время ожидания решения пользователя показывать отдельно от скорости агента. Для маленькой модели полезнее убрать ненужный полный prefill или ошибочный цикл read/edit/test, чем выиграть несколько процентов на генерации ответа.

## 5. Подтверждённые дефекты и риски

### F01. Ложный успех offline fallback тестов — КОД + ВОСПРОИЗВЕДЕНО

**Где:** `pideck-run-tests.ts`, `ZERO_FIXTURE_RUNNER`; `pideck-tool-router.ts`, обработка результата `run_tests`. [S07, S08]

При отсутствии pytest fallback вызывает `value()` и увеличивает `passed`, но не проверяет тип функции/результата. Для zero-argument `async def test_...` возвращается coroutine; тело не выполняется. Для generator-функции возвращается generator с тем же эффектом. Изолированные примеры с заведомым `AssertionError` внутри тела завершились кодом 0 и сообщением `1 passed`, маркер исполнения тела отсутствовал. В async-примере был `RuntimeWarning`.

Роутер затем интерпретирует `details.status === 0` как авторитетное подтверждение исправления и завершает scoped repair. Это не только косметическая ошибка отчёта. Исправление: **AG-01**.

### F02. PLAN называет самодекларацию проверкой — КОД

**Где:** `pideck-plan-ledger.ts`, `progressMarkers()` и `turn_end`. [S06]

`[DONE:n]` из текста модели переводит пункт в `verified`; все такие пункты дают `complete`. Маркеры ищутся по всему ответу, не только в строго валидированной финальной строке. Независимого подтверждения тестом, diff или результатом инструмента здесь нет. Это не обход пользовательского approval, но неверная семантика доверия к результату. Исправление: **AG-02**.

### F03. Отмена старта может задержать продолжение жизненного цикла — КОД + ГИПОТЕЗА интеграционного проявления

**Где:** `NativeLlamaController.java`, `monitorAndAdopt()` и `stopThen()`. [S11]

Оба пути используют один static single-thread executor. Monitor занимает его циклом до 240 секунд. Он проверяет `FAILED`, но не завершает цикл по совпадающему `STOPPED` и не имеет явного cancellation token. `stopThen()` немедленно отправляет команду остановки сервису, однако ожидание завершения и continuation ставит в очередь за этим monitor.

Следствие: **не сама отправка STOP**, а дальнейший restart/continuation потенциально ждёт оставшегося startup deadline. В аудите задержка на телефоне не измерялась. Исправление: **APP-01**.

### F04. Ограничение поиска применяется слишком поздно — КОД + ВОСПРОИЗВЕДЕНО для буферного контракта

**Где:** `pideck-code-nav.ts`, `ripgrep()` / `navigate()`. [S05]

Два `rg` уже запускаются параллельно, но `execFile` сначала собирает полный stdout с `maxBuffer = 256 KiB`. Только после завершения выбираются 12 путей и 24 совпадения. Большой репозиторий или частый термин способны превратить полезный частичный ответ в ошибку буфера. Изолированный producer на 300 KiB подтвердил `ERR_CHILD_PROCESS_STDIO_MAXBUFFER`; это проверка поведения `execFile`, не замер реального ripgrep. Исправление: **AG-03**.

### F05. Пустой поиск определяется по содержимому исходников — КОД + ВОСПРОИЗВЕДЕНО для предиката

**Где:** `pideck-context-guard.ts`, ветка old no-match search. [S04, S05]

Regex ищет `no matches`, `nothing found` и русские эквиваленты в произвольном тексте результата. Реальное совпадение вида `src/search.py:12:5: return "no matches"` проходит этот предикат. При выполнении дополнительных условий возраста и общего порога экономии ≥4 KiB такой результат может быть подменён маркером пустого поиска. Напротив, фактическая пустая строка `No filename or text match...` из `code_nav` этот regex не проходит.

Изолированно подтверждены оба несовпадения классификации; полный pipeline pruning не запускался. Исправление: **AG-03**, затем **PERF-02**.

### F06. Публикация alpha15 не подтверждает полноту asset-набора — ИСТОРИЯ + текущий снимок API

Для audited SHA main-run `35267941610` успешен. Tag-run `35267941789`, attempt 2, завершился ошибкой именно `Publish signed release assets`; build, подпись и загрузка Actions artifact прошли. Лог показывает `Error saving asset` и частично успешные загрузки. [S18, S19]

На момент чтения API APK имеет `state: uploaded`; `models-v2.json` и `pi-deck.cdx.json` имеют **`state: starter`, `digest: null`**. Часть metadata позже дозагружалась пользователем. Нельзя на основании этого объявлять APK недоступным или подпись сломанной; но полнота релизного набора не обеспечена. Точная причина серверной ошибки загрузки из доступного лога не установлена. Исправление: **APP-04**. [S20]

### F07. История и навигация интерфейса ограничивают рабочий сценарий — КОД

`DeckView` использует ScrollView + LinearLayout и удаляет из UI-проекции записи сверх 60. Полная история Pi от этого не объявляется потерянной. Завершённый ответ — TextView с подсветкой путей, не Markdown renderer. `lastWrittenPath` хранит только последний затронутый путь. Streaming уважает `isNearStreamEnd()`, но `addEntry()` и следовательно новые trace-события безусловно вызывают scroll-to-end. Исправления: **UX-01…UX-03**. [S09]

## 7. Производительность моделей и агентного цикла

### PERF-01. Измерять задержку полезного результата

**Изменить:** `GenerationSpeed.java`, `DiagnosticReport.java`, `NativeLlamaController.java`, bridge/event envelope и адаптер provider; добавить предлагаемый `InferenceTrace` без текста пользовательских запросов.

На один `operationId` записывать монотонные интервалы: очередь, загрузка модели, готовность provider, каждый provider round, prefill, native first token, первый видимый текст, первое успешно выполненное полезное tool-действие, decode, инструмент, ожидание approval, terminal. Отдельно учитывать input/output/reasoning tokens, фактические cached/evaluated tokens — только когда их сообщает runtime; неизвестное поле остаётся `null`, оценка маркируется.

У каждого измерения должны быть model SHA, runtime build, model/template/tool contract fingerprint, активные thread/affinity параметры, background/foreground, thermal signal, память и состояние charging. CPU/sysfs данные могут быть недоступны: это не нулевые значения.

**Приёмка:** cold/warm/replay/tool сценарии дают раздельные trace; все события связаны с правильной операцией; stale event не меняет её итог. P95 считается только при достаточной выборке; в кратком smoke публикуются число запусков и сами значения. Native tok/s никогда не выдаётся за скорость всей задачи. Существующую финальную TPS-метрику сохранить как одну из метрик, не как главный KPI. [S03, S10]

### PERF-02. Token- и cost-aware управление контекстом

**Изменить:** `pideck-context-guard.ts`, `pideck-local-cache.ts`, соответствующие extension/protocol tests. Добавить предлагаемый `ContextBudgetPolicy`, а не второй независимый слой обрезки.

Делить контекст на обязательную инструкцию/активную задачу, свежие доказательства, вспомогательные snippets и историю. Ограничение в байтах сохранить как защиту памяти, но семантический бюджет рассчитывать в токенах выбранного tokenizer. Сверять итоговый сериализованный запрос с реальным context window и резервом Pi; не вычитать один резерв дважды. Если точный tokenizer недоступен, оценка должна быть консервативной и явно неточной, а не «символы / 4» для любого языка.

В тёплой сессии переписывание раннего префикса может стоить дороже экономии. Решение о pruning должно учитывать `cacheState`, context headroom, объём реально сохранённых токенов и измеренную стоимость replay. Не использовать формулу «удалённые токены × число будущих ходов» без учёта cache hits: сохранённый warm prefix и так не обрабатывается полностью на каждом ходе.

При безопасном запасе окна сохранять append-only prefix; объединять очистки на границе задач. При угрозе переполнения — выполнить одну явную перестройку с новым fingerprint и безопасным `cache_prompt:false`. При холодном старте оценивать компактную ветку отдельно. Никогда не ослаблять проверку точного префикса ради процента cache hit. Unknown runtime/model capabilities → консервативный отказ от reuse. [S02, S04, S13]

**Приёмка:** изменения sampling-only полей не вызывают необоснованного replay; изменение tool schema, template, history или rules не переиспользует несовместимое состояние. Сжатие не удаляет обязательные ограничения, свежую ошибку теста или единственную копию доказательства. Full transcript не меняется; pruned artifact остаётся доступен по устойчивому идентификатору. A/B показывает выигрыш по времени задачи, а не только по числу байтов.

### PERF-03. Возобновление без неосознанного 8k replay

**Изменить:** существующие `SessionContract`, `SessionContextUsage`, `IdleShutdown`, startup/queued-prompt flow и UI выбора контекста. Существующее предварительное прогревание и smart idle не дублировать. [S01, S03, S10]

Перед холодным продолжением показывать выбор: полная история; новая компактная ветка с состоянием задачи; чистая сессия. Выбор нужен при существенной ожидаемой задержке, а не на каждом коротком prompt. Прогноз давать диапазоном на основе собственной статистики устройства и отмечать отсутствие данных.

Компактный checkpoint задачи: цель, подтверждённые ограничения пользователя, список затронутых файлов и их версии, diff/receipt IDs, результаты проверок, открытые вопросы, следующий шаг, ссылки на исходную сессию. Факты собирать детерминированно из runtime; необязательное LLM summary считать недоверенным пересказом и не запускать без бюджета. Само резюмирование может быть дорогим — его стоимость входит в измерение.

Ветка должна быть обратимо связана с полной историей; никаких скрытых replay или тихого стирания контекста. Старые approval не переносить. После смены модели/рабочей копии повторно читать нужные файлы и выдавать новые edit anchors.

**Приёмка:** у restart с большой историей нет обхода выбора через queued dispatch; компактная ветка сохраняет все заданные ограничения в тестовых задачах; full-session путь доступен. Нельзя рекламировать дисковый KV-cache для pinned Qwen hybrid runtime: в сохранённом эксперименте restore не ускорил первый запрос. Реальное cache restore допускается лишь как отдельная backend capability после restart-тестов. [S03]

### PERF-04. Единый бюджет задачи вместо независимых эвристик

**Изменить:** `pideck-tool-router.ts`, `pideck-adaptive-thinking.ts`, operation settings и tests. Уже есть ограничения 8/24 попыток и двух одинаковых вызовов, scoped repair, direct lookup и reasoning cap. Задача — сделать их согласованными и наблюдаемыми. [S08]

Предлагаемый `TaskBudget`: max provider rounds, generated/reasoning tokens, tool attempts, repeated-error allowance, wall deadline без approval time. Presets: короткий ответ, поиск/объяснение, scoped repair, глубокая задача. Настройки не должны расширять access profile. Маршрутизировать по явному выбору пользователя и ограниченным детерминированным признакам; не добавлять отдельный LLM-классификатор перед каждым запросом.

Retry policy зависит от причины: stale anchor → перечитать точный диапазон; invalid argument → одна коррекция; syntax/test assertion failure → исправление в допустимом scope; missing runner → `unsupported`; инфраструктурный сбой → ограниченный повтор без принуждения изменить исходник; отказ пользователя → без повторов. Сейчас scoped test failure блокирует тот же тест до source edit; эту ветку нельзя применять к любой инфраструктурной ошибке. [S08]

**Приёмка:** небольшой read-only запрос не требует обязательного PLAN; дополнительные round возникают только по понятной причине. Исчерпание бюджета сохраняет достигнутые изменения и честно показывает незавершённость, не превращается в `success`. Для mandatory-reasoning модели preset ограничивает допустимый reasoning, но не обещает неподдерживаемое «полное отключение».

### PERF-05. Калибровка CPU и режим длительной нагрузки

**Изменить:** `CpuProfile.java`, `ThermalHeadroom`, native-service policy; добавить предлагаемый `DevicePerformanceProfile`. Текущий выбор максимум пяти самых высокочастотных decode cores и первых восьми batch cores оставить fallback. В `CpuProfile` нет измеряемой оптимизации под конкретную модель и проверка directories сама по себе не является проверкой доступной online/allowed affinity. [S12]

По явному действию пользователя выполнять ограниченный sweep нескольких thread/batch/ubatch сочетаний, только поддерживаемых закреплённым runtime. Проверять реально применённые CPU sets. Ключ результата: device/SoC, OS/driver, runtime build, model SHA, context/cache format. Не переносить профиль между моделями автоматически.

Добавить режимы «Интерактивный», «Сбалансированный», «Экономный». Выбирать их по latency, качеству, потреблению памяти и sustained-нагрузке; одного cool TPS недостаточно. CPU/GPU частоты не «форсировать». Thermal API/performance hints использовать при поддержке устройства и ОС; ADPF допускает адаптацию performance-intensive приложений, но не обещает конкретный cpuset или отмену системного throttling. [S21]

Policy использует hysteresis и cooldown, а не переключает потоки на каждом событии. Изменения, требующие пересоздания native context, применять между задачами с учётом цены потерянного кэша. Не конкурировать за CPU с массовой индексацией или установкой пакетов во время inference.

**Приёмка:** 20-минутный sustained-сценарий без crash/LMK и без незавершённых управляющих операций; график throughput/thermal/RAM прилагается. При отсутствии датчиков поведение предсказуемо. Background mode явно не обещает foreground throughput; существующий механизм предупреждения сохранить.

### PERF-06. Выбирать модель по полезной работе, не только по TPS

**Изменить:** `models-v2.json`, `ModelCatalog`, `ModelSpec`, модель допуска и benchmark reports. Сохранить текущую явную ручную выборку и SHA pinning. Текущая QAD-лестница основана на кратких latency-свидетельствах; полный 28-task admission остаётся незавершённым. [S01]

Допуск привязать к комбинации model artifact + runtime + template + profile + device class. Отдельные показатели: русский язык, валидность tool arguments, навигация, точность edit, test correctness, исполнение scope, длинная сессия, память, cold/warm latency и энергия на завершённую задачу. Метрики качества не заменять единичным smoke `PIDECK_OK`.

Новый default допускается после полной существующей suite и новых regression-cases F01–F05. Быстрая модель с большим числом ошибок может проиграть более медленной по времени проверенной задачи. Escalation на более сильную модель — один явный переход с оценкой загрузки; не держать две крупные модели одновременно на 12 GiB и не переключать их на каждом tool round.

Backend selection сделать capability-based интерфейсом, но не переписывать рабочий llama adapter заранее. Проверки GPU/MNN/новой llama версии — opt-in isolated candidates. Исторические отрицательные результаты относятся к конкретному backend/драйверу; новый эксперимент оправдан существенным изменением этой комбинации, не только новым номером сборки. Speculative decoding — только если draft/verification действительно снижают end-to-end время при допустимой RAM; обещанного ускорения в ТЗ нет. [S03]

**Приёмка:** неизвестная модель не подменяется рекомендацией; ручной выбор не мигрирует без решения пользователя; отчёт содержит полную конфигурацию и сравнение качества. Кандидат без доказанной корректности не получает статус «рекомендуется».

## 8. Возможности и достоверность агента

### AG-01. Структурированный test verdict и честный fallback — P0

**Изменить:** `pideck-run-tests.ts`, все потребители в `pideck-tool-router.ts`, tests/extensions и protocol tests. [S07, S08]

Вместо «exit 0 = всё проверено» возвращать `TestReceipt`: runner/version, operation ID, workspace snapshot, argv fingerprint, набор/фильтр тестов, selected/passed/failed/skipped, termination reason, exit code, длительность и artifact ID полного вывода. Вердикты: `passed`, `failed`, `no_tests`, `unsupported`, `timed_out`, `cancelled`, `output_limit`, `infra_error`. Не сводить любую остановку сигналом к таймауту, как делает текущий `timedOut: outcome.signal !== null`.

Offline fallback не является pytest. Минимальный безопасный патч: принимать только явно поддержанные синхронные zero-argument функции; coroutine/generator/async generator и awaitable/generator результаты — `unsupported`, не `passed`. Не пытаться незаметно реализовать fixtures, async plugins, parametrization и pytest `-k` через substring. Ограничение 200 файлов должно приводить к явному partial/unsupported результату, а не заявлению о проверке всего каталога. При отсутствии поддержанного runner агент предлагает доступный способ проверки, не устанавливает произвольные зависимости автоматически.

`passed` разрешён только при подтверждённом выполнении непустого выбранного набора и поддержанной семантике. Неизвестный test count не надо придумывать: такой run может подтверждать успешную команду, но не статус «тесты пройдены». Запуск существующего проекта может выполнять произвольный код; доверие к репозиторию и разрешение исполнения обязательны.

**Приёмка:** async/generator примеры из пакета больше не дают `passed`; отмена отличается от deadline и output limit; missing pytest не рисуется assertion failure; zero tests не зелёный; output overflow не оставляет дочерние процессы. Тесты с повреждённым окружением не вынуждают агента менять исходник перед допустимым повтором. Старые receipts после новой правки становятся устаревшими.

### AG-02. PLAN: декларация, выполнение и проверка — разные состояния — P0

**Изменить:** `pideck-plan-ledger.ts`, `PlanLedger.java`, `PlanDecisionCardView`, bridge checkpoint schema. Сохранить read-only planning pass и решение пользователя. [S06]

Состояния пункта: `pending`, `active`, `done_unverified`, `verified`, `blocked`, `cancelled`; тип подтверждения — `test`, `inspection`, `artifact_check`, `user_acceptance`. Текстовый `[DONE:n]` может стать только сигналом `done_unverified`. Для `verified` runtime должен сопоставить требуемое подтверждение с текущим snapshot и пунктом плана. Простому исследовательскому шагу не нужен фиктивный тест, но «проверено чтением» нельзя выдавать за проход тестов.

Вместо свободного сканирования всего сообщения внедрять отдельный typed progress event, если это поддерживается pinned Pi API; иначе строгий fenced/terminal protocol с явным parser. Любое предложение модели валидируется хостом. Примеры маркеров внутри кода, цитат, файла или tool output не завершают план.

Approval привязать к plan revision, operation, workspace, scope и expiry. Изменение согласованного scope требует нового решения. При restart план сохраняется как interrupted/blocked; продолжение — только явное, после сверки текущих файлов. Не вводить молчаливый auto-resume.

**Приёмка:** три `[DONE]` без доказательств не дают статус «всё проверено»; тест до последней правки не подтверждает новую версию; timeout/deny/disconnect не запускает выполнение; старое approval не подходит новому плану. План виден вместе с причинами blocked и ссылками на evidence.

### AG-03. Producer-bounded поиск и типизированное отсутствие результатов — P0/P1

**Изменить:** `pideck-code-nav.ts`, `pideck-context-guard.ts`. [S04, S05]

Сначала убрать content-regex классификацию empty из pruning: использовать `details.fileCandidates`, `details.textMatches`, `status`, `truncated`. Для legacy-результата без metadata безопаснее сохранить текст, чем угадать по фразе из исходника.

Затем заменить полный capture на streaming producer с ограничением строк/байтов/времени уже при чтении stdout. Достигнутый предел — `partial`, а не произвольная ошибка `maxBuffer`; остановка producer по нашему лимиту отличается от crash. Удаление/пропуск хвоста обязательно маркируется. Результат содержит точный scope, совпадения с путями/строками, полноту поиска и способ сузить запрос. Порядок должен быть детерминированным, если используется continuation; нельзя обещать устойчивую пагинацию по меняющемуся дереву без snapshot.

Существующий parallel read-only поиск сохранить. Для больших проектов добавить лёгкий кэш перечня файлов и деклараций с ignore-rules; устаревание по fingerprint/mtime плюс проверка файла перед редактированием. Полноценный vector DB или постоянно работающий LSP не требуются для первого этапа.

**Приёмка:** большой искусственный репозиторий и частый термин возвращают bounded partial result без buffer exception; источник с фразой `no matches` не теряется; настоящий empty распознаётся структурно; `cancel` останавливает оба producer; обход path/symlink scope остаётся запрещённым. Поиск, прерванный лимитом, не объявляет «во всём проекте ничего нет».

### AG-04. ChangeSet: управляемые многофайловые правки — P1

**Изменить:** существующий `pideck-hashline-edit.ts` и интерфейс подтверждения; добавить предлагаемые `ChangeSetStore` и `ChangeReceipt`. Точную read-before-write модель и atomic single-file replace сохранить. [S02]

Одна задача должна собирать список всех правок с base hash, new hash, unified diff, принадлежностью операции и состоянием применения. Перед применением validate весь заявленный набор: scope, разрешения, свежесть anchors, текущие инструкции и отсутствие неожиданных изменений. Сохранять preimages/журнал восстановления только для затрагиваемых файлов, с квотой.

Группа отдельных rename не является атомарной транзакцией файловой системы. Реализовать журнал состояний `prepared → applying → applied/partial → verified`, восстановление после сбоя и compensating rollback. Rollback разрешён только если текущие байты совпадают с результатом собственной правки; чужие последующие изменения не перезаписывать. Не использовать `git reset --hard`/`git clean` как откат задачи и не трогать пользовательский index.

Для изолированной работы с крупным рефакторингом можно предложить отдельный worktree, но не навязывать его для каждого телефонного проекта. Изменение тестов по умолчанию не должно автоматически засчитываться как независимое доказательство исправления: scope тестов фиксируется и изменения показываются отдельно.

**Приёмка:** конфликт любого base hash останавливает preflight; process death между файлами восстанавливается в понятное partial-состояние; rollback сохраняет чужую правку; UI показывает все изменённые файлы, а не `lastWrittenPath`; повтор tool call с тем же mutation ID не применяет правку второй раз.

У проекта есть canonical root, display name, trust/access profile, разрешённые execution capabilities, выбранная модель, язык/stack, пользовательские инструкции, команды проверок и связанные сессии. Перед отправкой prompt пользователь видит активный проект. Смена проекта не переносит approvals, приватный read cache или edit anchors.

Команды выбираются из явного project config или подтверждённого обнаружения, не из строки модели, превращённой в shell. Unknown stack → обычный инструмент с явным ограничением проверки. Каждому pack задать version, provenance, необходимые права, limits и schemas. Подключать только по потребности, сохраняя действующую политику provider schema и учитывая цену нового prefix. Параллелить ограниченные независимые чтения, не несколько LLM inference и не конфликтующие мутации.

**Приёмка:** запрос без pack не платит его schema/context cost; tool result и содержимое репозитория не запускают новый pack сами; сеть не включается вследствие инструкции из файла; при удалении проекта удаляется его индекс, не общая история соседнего проекта.

Развести три независимые оси: **назначение** Chat/Agent/Plan; **доступ** Read-only/Confirm changes/Autonomous; **расход вычислений** Fast/Balanced/Deep. Deep не даёт запись, Agent не равен shell permission, Fast не является гарантией отключения mandatory reasoning. В обычном UI — короткие подписи и текущий проект; технические профили, thread counts, runtime details — в раскрываемой диагностике.

Контекстная кнопка «Ускорить» заменить на «Сжать контекст» с пояснением потери подробностей и возможного разового replay. Настройку «Максимальная скорость» объяснять реальным эффектом, не как снятие системного throttling. Очередь одного prompt показывать явно; замена/редактирование queued сообщения не должна молча отправлять старый вариант.

**Приёмка:** cancelled/unsupported/test-failed визуально не совпадают с success; `done_unverified` не зелёная «проверено»; ожидание approval не считается зависанием; счётчик времени разделяет активную работу и пользовательскую паузу.

### UX-04. Setup и recovery как один управляемый маршрут — P1

**Изменить:** `CoreRootView`, install/download flow, `ModelDownloadManager`, readiness presentation. Сохранить двойную проверку и приватную установку модели; не менять её на прямой запуск из Downloads ради скорости. [S01, S02]

Последовательность: обнаружение/подключение Termux → установка согласованного runtime → выбор подходящей модели → скачивание → проверка → установка → короткая проверка готовности. Пользователь видит один маршрут, хотя внутренние операции остаются раздельными и восстанавливаемыми. Пояснять источник загрузки, размер, RAM и временную потребность в storage.

После сбоя выделять конкретный слой: Termux link, runtime, native model, authenticated bridge, конкретная задача. Кнопка ремонта действует только на повреждённый слой и заранее сообщает о потере warm state. Не предлагать полную переустановку при временной недоступности bridge. Download/resume проверяет поддержку диапазонов и идентичность объекта, иначе безопасно начинает файл заново.

**Приёмка:** закрытие Activity или ошибка сети не теряют установку/докачку; corrupt GGUF никогда не становится runnable; при недостатке storage ошибка появляется до начала тяжёлой копии; recovery не удаляет сессию и не запускает заново уже исполнившуюся мутацию.

## 10. Архитектура и жизненный цикл приложения

### APP-01. Отменяемый startup и защита поколений сервера — P0

**Изменить:** `NativeLlamaController.java`, соответствующие события `NativeLlamaService`, coordinator/startup tests. [S11, S14]

Заменить длительный blocking monitor на scheduled probes с сохраняемым cancellation handle. Управляющие операции STOP/ABORT/смена модели не должны ждать очередь probes, bulk I/O или network timeout. Каждая проба проверяет `operationId` и отдельный `serverGeneration`, состояние active/terminal и отмену до запроса, после запроса и перед adoption.

`STOPPED`, отмена и смена поколения завершают старый monitor. Старый catch/finally не останавливает новый сервер, не очищает его metadata и не публикует failure в новую операцию. `stopThen` завершается ровно один раз с явным результатом `stopped/failed`, а не безусловным продолжением после timeout. Action inference-active/idle также коррелировать с актуальной задачей, чтобы поздний idle не снял wake lock новой генерации.

Короткие HTTP deadlines сохраняются; cancellation должна прерывать ожидание, а не только проверяться через полный startup timeout. Реальное дерево дочерних процессов останавливать контролируемо: известная process group/identity, мягкое завершение, затем ограниченная эскалация; не `killall` по общему имени.

**Приёмка:** fake-clock/startup-never-ready тест: cancel освобождает continuation независимо от 240-секундного deadline; duplicate STOP безопасен; поздний health/adoption не воскрешает остановленную модель. Цель на референсном телефоне: UI acknowledge ≤250 ms, разрешение отменённого startup control-flow ≤2 с, завершение известного native процесса ≤5 с с явной ошибкой при недостижении. Числа — цели измерения, не результат этого аудита.

### APP-02. Извлечь операционное состояние из MainActivity — P1

`MainActivity.java` имеет 248 151 байт и множество независимых mutable flags: server/bridge readiness, busy, queue, compaction, approval, inference, retries. Часть правил уже выделена в core; архитектурная документация прямо признаёт оставшееся presentation wiring. Размер файла сам по себе не доказывает торможение, но осложняет проверку состояний. [S02, S10]

Предлагаемая структура:

```text
MainActivity + существующие Java Views
                ↓ пользовательские intents
DeckViewModel / presenter → immutable DeckUiState
                ↓ commands
RuntimeSessionController (application/service scope)
    ├─ существующий OperationCoordinator / OperationStore
    ├─ NativeLlamaController → NativeLlamaService
    ├─ RpcBridgeClient → Pi runtime
    ├─ SessionRepository / transcript projection
    ├─ WorkspaceRepository
    └─ ModelInstallCoordinator / ArtifactRepository
```

Новые названия здесь — проектируемые компоненты. `ViewModel` не является владельцем долгой операции и не обеспечивает восстановление после process death: это обязанности runtime/controller + durable store. Activity отвечает за отображение, lifecycle подписок, permissions и пользовательскую навигацию, не за истину «сервер готов».

Вводить state reducer по одному flow: startup, затем prompt/queue, затем approval, затем session/model selection. Сначала characterization tests существующего поведения; только потом перенос. Разделить control executor, bounded bulk I/O и фоновые задачи, сохраняя сериализацию мутаций. Рефакторинг Java→Kotlin/Compose не входит в необходимый объём.

**Приёмка:** rotation/recreation и два подписчика UI не создают второй prompt; dialogs создаются из state, а не являются источником истины; listeners не удерживают уничтоженную Activity; один event даёт детерминированный новый state. Сохранённые protocol tests проходят после каждого извлечения.

### APP-03. Типизированные события, проекция и диагностика — P1

**Изменить:** существующие `schemas/`, `BridgeEvent`, `OperationRecord`, Python bridge и TS emitting code. Новые поля — совместимая версия контрактов, а не параллельный протокол. [S02]

Единый envelope для новых evidence-событий: protocol version, bridge instance, sequence, operation/task/session/workspace IDs, server generation, event type, timestamp и typed payload. Не дублировать уже существующие UUID и reconcile — расширять их. Неизвестный тип/версия не становится success; деградировать безопасно и запрашивать snapshot.

Полная история Pi — authoritative; Android SQLite-проекция — индексируемый read model, восстанавливаемый по session cursor. Mutation receipts и результаты проверок связываются с этой историей. Для окон «операция совершилась, ответ потерян» нужен `effect_unknown` и reconcile, не автоматический повтор команды. Универсальный exactly-once для произвольного shell через процессные сбои обещать нельзя; managed file mutations делаются idempotent по mutation ID и snapshot.

Диагностический экспорт содержит версии, фазы, длительности, typed errors, размеры и fingerprints. По умолчанию без prompt, исходников, API keys, полного домашнего пути и tool stdout. Расширенный экспорт — после preview и отдельного решения. Историю задач и диагностический журнал не смешивать.

**Приёмка:** контрактные fixtures проходят в Java/Python/TS; пропуск event sequence вызывает reconcile без prompt replay; старый/new envelope читаются по migration policy; секреты-маркеры из fixture отсутствуют в обычном diagnostic bundle.

### APP-04. Релиз сначала проверяется полностью, потом публикуется — P0

**Изменить:** `.github/workflows/build.yml`; добавить предлагаемый `tools/publish_release.py` и `tools/verify_release_bundle.py` либо эквивалентные шаги. [S15, S18–S20]

Сохранить правильные существующие меры: подписывать уже протестированный unsigned APK, проверять certificate SHA, signed tag и отсутствие debug flag, публиковать supply-chain metadata. Добавить manifest ожидаемых assets, SHA и source commit.

Flow: подготовить draft → загрузить assets с bounded retry → проверить `uploaded`, размеры и фактические SHA скачанного содержимого → проверить manifest и подпись APK → опубликовать. Это не настоящая атомарная транзакция GitHub, но пользователь не должен получать готовый release до проверки целостности набора.

Повторный запуск публикации использует **тот же** подписанный артефакт. Совпадающие assets не перезаливаются; `starter`/ошибочные assets удаляются и заменяются только при строгой проверке принадлежности текущему release. Не перемещать tag. Для существующего опубликованного релиза repair idempotent и журналируемый; совпадение имени не является проверкой hash.

**Приёмка:** искусственный сбой загрузки одного metadata-файла не публикует новый draft; retry доставляет полный набор без пересборки; `starter` не считается успехом; SOURCE_COMMIT, manifest, APK и signing certificate согласованы. Для alpha15 отдельно выполнить repair/verification; API-аудит состояния сам по себе не меняет релиз.

### APP-05. Хранилище, артефакты и миграции — P1

**Изменить:** `DeckPreferences`, native/model stores, context tool-results storage и session export. Простые settings оставить preferences; историю, поиск и связанные receipts хранить в структурированном store.

В `pideck-context-guard.ts` большие tool results сохраняются синхронно и очищаются по глобальному лимиту 48 файлов. Это ограничивает рост, но не гарантирует жизнь ссылки из старой сессии. Заменить привязку к произвольному path на `artifactId + content hash + owning session/operation + retention state`. Переход к асинхронной записи допустим лишь после надёжного сохранения содержимого, на которое уже выдана ссылка. Активные доказательства pin; GC удаляет только unreferenced/expired артефакты по квоте и явно показывает недоступность старых. [S04]

Миграции additive/versioned, экспорт перед потенциально разрушающим изменением, восстановление после сбоя без полуобновлённого store. Экспорт проекта/сессии не содержит auth tokens; большие GGUF исключаются по умолчанию. Импорт не доверяет executable config и не восстанавливает approvals. Данные разных workspace не смешиваются.

Private verified GGUF и модельный checksum остаются обязательными. В UI показывать total storage с учётом incoming/private copies и временных файлов; cleanup не удаляет выбранную или живую модель. Освобождение download copy — только после durable verified private install.

**Приёмка:** удаление старого лога не ломает активную проверку; квота диска соблюдается; внезапный process death при миграции восстанавливается; corrupt/imported архив не повышает права; модель не запускается из непроверенной общей памяти.

### APP-06. CI и приёмка реального поведения — P1

Workflow уже запускает Java unit/lint, Python и реальные Pi protocol/extension checks. Его `assembleDebugAndroidTest` **собирает**, но не запускает instrumentation; это нельзя считать UI acceptance. [S15]

Разделить быстрые host/contract jobs и тяжёлое получение/сборку native runtime. Кэш native artifacts привязать к исходникам, патчам, NDK/CMake и flags; не использовать mutable cache как источник доверия. Actions фиксировать полными SHA, зависимости — lock/verification metadata; обновлять отдельным PR с объяснимыми изменениями. Это ускоряет разработку и повышает воспроизводимость, но не является ускорением модели у пользователя.

Запускать instrumentation с fake bridge на эмуляторе для UI/lifecycle и на референсном телефоне для native inference/thermal/abort. Проверять не только zipalign, но и загрузку native runtime на поддерживаемых конфигурациях страниц памяти/Android. Hardware gate связывать с конкретным source commit и SHA подписанного APK, не с «похожим debug build прошлой alpha».

Fault injection: process death до/после file rename, bridge disconnect при approval, event gap, network/download failure, disk full, malformed model/tool result, stale snapshot, повторная доставка terminal, cold start cancel. В release gate нет красных correctness-тестов и нет пропущенных обязательных аппаратных сценариев.

**Приёмка:** test reports позволяют отличить host, emulator и handset evidence; release promotion не выдаёт compile-only за executed test; regression fixtures F01–F05 добавлены в репозиторий, не остаются только внешним аудитом.

## 11. Предлагаемые контракты данных

Это проектируемые структуры, не существующая API-схема. Имена/типы должны быть согласованы в `schemas/` и с pinned Pi integration seam до реализации.

```typescript
type VerificationStatus =
  | "passed" | "failed" | "no_tests" | "unsupported"
  | "timed_out" | "cancelled" | "output_limit" | "infra_error";

interface TestReceipt {
  schemaVersion: 1;
  receiptId: string;
  operationId: string;
  workspaceId: string;
  snapshotId: string;
  runner: { name: string; version: string | null };
  invocationFingerprint: string;
  selected: number | null;
  passed: number | null;
  failed: number | null;
  skipped: number | null;
  status: VerificationStatus;
  exitCode: number | null;
  durationMs: number;
  artifactId: string | null;
}

interface NavigationResult {
  schemaVersion: 1;
  status: "complete" | "partial" | "failed" | "cancelled";
  scope: string;
  snapshotId: string | null;
  fileCandidates: number;
  textMatches: number;
  truncated: boolean;
  artifactId: string | null;
}

interface PlanStepEvidence {
  stepId: string;
  planRevision: string;
  state: "pending" | "active" | "done_unverified" | "verified"
       | "blocked" | "cancelled";
  verificationKind: "test" | "inspection" | "artifact_check"
                  | "user_acceptance" | null;
  evidenceIds: string[];
}
```

Валидация хоста: `TestReceipt.status = passed` несовместим с `selected = 0` или неизвестным подтверждением фактического набора; `snapshotId` совпадает с проверяемой ревизией. Receipt может подтверждать отдельную команду/файл, а не обязательно все шаги плана. `NavigationResult` с `partial` и нулём найденных совпадений не доказывает их отсутствия во всём scope.

## 12. Матрица приёмки и экспериментальная методика

### 12.1. Обязательная correctness-регрессия

| Сценарий | Ожидаемый результат |
|---|---|
| Нет pytest, async/generator zero-arg test с падающим телом | `unsupported` либо корректный supported runner; никогда ложный `passed` |
| Ноль выбранных тестов / неизвестный сбор тестов | Не «проверено тестами» |
| Отмена, timeout, output cap | Три разные причины; корректное завершение process tree |
| `[DONE:1]` в кодовом примере или без receipt | План не становится verified |
| Реальная найденная строка содержит `no matches` | Сохраняется как совпадение |
| Большой вывод поиска | Partial result, не buffer exception и не ложный empty |
| Отмена native STARTING | Monitor отменяется, поздний health не adopt-ит сервер |
| Смена модели во время старого failed probe | Старое поколение не останавливает новое |
| Потеря ответа после мутации | Reconcile / effect_unknown, без скрытого повторного применения |
| Сбой после первого файла ChangeSet | Явное partial + безопасное восстановление |
| Stale anchor / внешнее изменение перед rollback | Отказ перезаписи, сохранение чужих данных |
| Чтение истории при новых tool rows | Позиция не скачет к концу |
| Process death с draft/approval | Draft восстанавливается; approval не исполняется само |
| Upload asset остаётся starter | Публикация не считается завершённой |

### 12.2. Производительность: цели, не установленные факты

Для каждой серии фиксировать commit/APK SHA, runtime/model/template hashes, реальные параметры, контекст, состояние памяти, charging, foreground/background, thermal. Различать native restart с тёплым OS page cache и настоящий холодный запуск; не называть первое «полностью холодным диском».

Минимальная матрица: короткий Chat; первый Agent запрос; warm follow-up; cold 8k replay; explicit single-file repair; многошаговая задача; большой repo navigation; 20 минут непрерывной работы; background/возврат на экран. Существующую 28-task suite использовать как минимум, не заменить на набор удобных latency probes. Включить незнакомые русские формулировки, чтобы router не «улучшался» под несколько строк benchmark.

Сравнения делать попарно с чередованием порядка и контролем thermal/memory. Для дорогостоящих cold/repair кейсов минимум пять валидных пар с публикацией всех значений; такой объём не даёт уверенной P95. Для warm P95 — отдельная серия не менее 100 запросов с описанием распределения и доверия. Исключённые запуски и причины публикуются, а не удаляются из отчёта без следа.

**Предлагаемые продуктовые gate:** warm TTFT короткого нового запроса P50 ≤1 с / P95 ≤3 с в оговорённой foreground-конфигурации; реакция UI ≤100 ms; отмена по APP-01; улучшение медианы end-to-end времени на целевом наборе задач хотя бы на 25% при отсутствии регрессии correctness. Для decode оптимизации допустимый регресс на прочих обязательных сценариях заранее зафиксировать, например не более 5%; выбирать итог по времени и качеству задачи, а не по одному TPS.

Эти цели не распространяются автоматически на длинный uncached prompt, горячий телефон, background cpuset или другую модель. Если цель не достигнута, изменение нельзя рекламировать как ускорение; качественный функциональный выигрыш оценивается отдельно и явно.

### 12.3. Методика контроля качества модели

Сравнивать исходный baseline и кандидат на одинаковых fixtures, запрещая оценивание самим исполняющим агентом. Успех — внешняя проверка scope, результирующего diff и тестов. Шаги «не нанесён ущерб» и «задача решена» — разные исходы: безопасный отказ не должен повышать coding score как успешный ремонт.

Порог допуска качества зафиксировать до прогона по категориям существующего benchmark. Не менять default только потому, что кандидат выиграл один кейс или прошёл валидный tool-call. Для full admission все обязательные категории должны быть выполнены; hardware/security failures — блокирующие независимо от среднего балла.

Исправить AG-01, AG-02, content-classification часть AG-03, APP-01 и APP-04. Внести regression fixtures до исправления; показать red→green на штатных suites. Здесь не менять модель, system prompt целиком, UI framework и backend. Результат: успех больше нельзя получить без выполненной проверки, запуск корректно отменяется, release проверяется целиком.

### Пакет B. Измерение и bounded execution

PERF-01, streaming producer AG-03, typed errors/receipts и PERF-04. Получить воспроизводимый baseline на референсном устройстве. Нельзя внедрять следующий пакет и одновременно менять model artifact — иначе эффект контекста неотделим от смены модели.

### Пакет C. Контекст и возобновление

PERF-02/03 и artifact retention часть APP-05. Сравнить warm prefix preservation, compact branch и full replay. Feature flags: `context_budget_v2`, `session_handoff_v1`; default включать только после correctness и latency gate. Полная история всегда остаётся доступной.

### Пакет D. Рабочий интерфейс и состояние приложения

Постепенный APP-02/03, UX-01…05, AG-04/05. Начать со scroll policy и Markdown, затем pagination, Changes/Test panels и WorkspaceProfile. Не блокировать небольшие UX-исправления полным извлечением MainActivity, но не добавлять в неё новую бизнес-логику.

### Пакет E. Калибровка и новые возможности

PERF-05/06, AG-06. Более сильные модели и backend-кандидаты оцениваются поверх уже исправленного runner. Любая модельная «победа», полученная до устранения ложных verdict, требует перепроверки в затронутых сценариях.

## 14. Что сознательно не делать

Не переписывать приложение целиком на Compose/Rust/другой agent framework ради предполагаемой скорости. Не заменять строгий prefix guard «похожестью контекста». Не включать дисковый KV-cache для неподтверждённого hybrid state. Не поднимать число потоков без сравнения и thermal-контроля. Не делать постоянный LLM-router, multi-agent swarm или две resident модели на референсном телефоне. Не выполнять полную индексацию при каждом prompt. Не рекламировать GPU по факту успешного старта backend без стабильного decode. Не считать тестирование проекта безопасным чтением. Не возвращать raw shell/network access через скрытые плагины. Не выдавать сокращение prompt на 30% за такое же ускорение всей задачи.

## 15. Definition of Done для каждого изменения

Изменены source, контракт, fixtures и пользовательское описание; pinned Pi compatibility сохранена либо обновлена отдельным доказанным migration. Есть тест исходного дефекта, отрицательный сценарий и failure/recovery сценарий. Для optimization — paired baseline/candidate report с одинаковой моделью и устройством; для UX — executed UI test, не только compilation. Секреты не попали в diagnostic export. Feature flag отключает новый policy без потери данных; миграция имеет восстановление. Документация различает implemented, host-tested, handset-tested и model-admitted. Готовый release содержит проверенный полный набор артефактов.

## 16. Материалы изолированных проверок

В этом пакете находятся `reproduce_findings.py` и `reproduction-results.json`. Запуск:

```bash
python3 reproduce_findings.py --output reproduction-results.json
```

Скрипт использует временные файлы и локальные subprocess; сеть, Android и установленный Pi не нужны. Node требуется только для трёх JS-проверок. Exit 0 означает, что **исходные проблемные свойства воспроизведены**, а не что приложение корректно. После исправления проекта этот внешний скрипт сам не меняется: перенести соответствующие fixtures в штатные tests и проверять реальные функции.
